# 思考指南

> **目的**：扩展思考范围，发现可能遗漏的问题。

---

## 为什么需要思考指南？

**多数 bug 和技术债来自“没想到这一点”，而不是能力不足**：

- 没想到层与层边界会发生什么 → 跨层 bug
- 没想到代码模式正在重复 → 到处都是重复代码
- 没想到边界情况 → 运行时错误
- 没想到未来维护者 → 代码难以阅读

这些指南帮助你在编码前**提出正确的问题**。

## 项目文档语言（强制）

- `.trellis/spec/**` 以及项目中新建或修改的需求、设计、实现说明、Review 记录和维护文档，必须以简体中文为主要语言。
- 代码标识符、API 字段、错误码、文件路径、命令、配置 key、协议名、库名和必须精确匹配的外部术语保持原样，不做强制翻译。
- 没有准确中文译法的英文术语可以保留；首次出现且可能产生歧义时，必须用简体中文解释。
- 代码示例中的字符串只有在不影响契约、测试和复制使用的前提下才翻译。
- Review 新增或修改文档时，必须检查本节；纯英文正文视为未满足规范。

## Git 提交规范（强制）

- 所有 commit 必须使用 Conventional Commits 格式：`<type>(<scope>): <中文摘要>`。`scope` 必填，使用能准确描述任务边界的小写英文或 kebab-case 标签。
- `type` 使用约定式提交的标准类型，例如 `feat`、`fix`、`docs`、`refactor`、`test`、`chore`、`build`、`ci`、`perf` 或 `style`。
- Commit message 的摘要必须以简体中文书写；技术标识符可保持原样。摘要应说明结果，不写过程性套话。
- 每个 commit 都必须包含与摘要之间空一行的 body。Body 必须以简体中文为主，至少说明本次改动的主要内容和目的。
- 提交前必须使用 `git status --porcelain` 和 `git diff` 列出脏文件，并区分当前任务与无关变更。
- 只允许暂存当前任务明确涉及的文件，使用 `git add -- <明确路径列表>`。禁止使用 `git add .`、`git add -A` 或可能包含无关文件的宽泛通配符。
- 不认识、无法确认归属或属于并行工作的脏文件必须保持原样，不得暂存、修改或提交。
- 每个 commit 只包含一个连贯的任务单元。提交后必须检查 `git show --stat --oneline HEAD` 和 `git status --short`，确认提交范围与剩余脏文件符合预期。
- Trellis 包装命令若生成的 commit 不符合本规范，必须使用其 `--no-commit` 等选项关闭自动提交，再对产生的当前任务文件创建合规 commit；禁止用 amend 修补不合规提交。
- 当前任务尚无工作 commit，且任务成果、质量门禁和 spec 更新已经全部完成时，必须先运行 `task.py archive <task-name> --no-commit`，再把任务成果、spec 更新和归档状态放入同一个 commit。禁止先提交成果、随后只为归档再创建第二个 commit。
- 当前任务已经存在多个有独立意义的工作 commit 时，不得仅为减少提交数量而重写历史；归档变更应创建一个符合本规范的独立 commit。已经推送或被其他工作引用的历史尤其不得在没有用户明确授权时重写。

一次性交付任务的正确顺序：

```text
完成任务成果与质量检查
→ 更新 spec
→ task.py archive <task-name> --no-commit
→ 只暂存当前任务成果、spec 和归档文件
→ 创建一个带 scope 与中文 body 的约定式 commit
```

正确示例：

```text
docs(bootstrap): 完成项目启动规范

整理产品需求、技术设计和分层开发规范。
为后续实现提供统一的中文契约与质量门禁。
```

错误示例：

```text
update docs
```

错误原因：缺少约定式 `type`、必填 `scope`、中文摘要和中文 body。

## 快速参考：思考触发条件

### 何时思考跨层问题

- [ ] 功能涉及 3 层以上（API、Service、Component、Database）
- [ ] 数据格式会在层之间变化
- [ ] 多个使用方需要同一份数据
- [ ] 不确定某段逻辑应该放在哪一层
- [ ] 正在添加事件类别、JSONL 记录、RPC payload 或配置字段
- [ ] UI/命令代码开始直接断言原始 payload 字段

→ 阅读[跨层思考指南](./cross-layer-thinking-guide.md)

### 何时思考代码复用

- [ ] 正在编写与现有代码相似的代码
- [ ] 发现同一模式重复了 3 次以上
- [ ] 正在给多个位置添加新字段
- [ ] **正在修改任何常量或配置**
- [ ] **正在创建新的 utility/helper 函数** ← 先搜索！
- [ ] 两个文件分别用局部类型断言读取同一个无类型 payload 字段
- [ ] 多个分支根据 `kind`/`action` 更新同一份派生状态

→ 阅读[代码复用思考指南](./code-reuse-thinking-guide.md)

### 项目必须通过的测试门禁

所有前端、API、数据库、资源和配置变更都必须遵循[测试策略](./testing-strategy.md)。

### 验证 AI 交叉 Review 结果时

- [ ] Review 方声称“用户输入可能是恶意的” → 检查实际数据来源（内部 manifest、用户配置还是外部 API？）
- [ ] Review 方指出“缺少校验” → 数据是否来自可信内部源？
- [ ] Review 方声称“行为改变” → 阅读代码注释，确认是否为有意设计。
- [ ] Review 方在测试中发现“bug” → 在脑中删除被测功能；测试是否仍会通过？如果会 → 这是自证式测试。

**AI Review 常见误报模式**：

1. **混淆信任边界**：把内部数据（例如 bundle 内的 JSON manifest）当成不可信外部输入
2. **忽略设计注释**：把代码注释中记录的有意行为标为 bug
3. **误读变量**：没有追踪变量的真实定义（例如 Map 的 key 是路径还是名称）

**验证规则**：每个 CRITICAL/WARNING 发现都必须先对照实际代码验证，再确定优先级。AI Review 应预留约 35% 的误报率。

## 修改前规则（关键）

> **修改任何值之前，一律先搜索！**

```bash
# 搜索即将修改的值
grep -r "value_to_change" .
```

这一习惯可以防止大部分“忘记同步修改 X”的 bug。
