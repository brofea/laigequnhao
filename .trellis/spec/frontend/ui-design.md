# V2 UI Design Language

> 版本：0.1.0 candidate
> 状态：T02 原型已实现，候选规范待四轮视觉评审和用户最终确认
> 主要参考：HeroUI v3 官方文档/仓库
> 表面参考：Neumorphism 一般设计规律及 `.references/neumorphism-example` 中的 MIT 示例
> 本轮方向确认：2026-08-01，用户确认“HeroUI 语义结构与可访问性优先 + 轻量新拟物表面”
> 适用范围：V2 前端；正式生产页面须由后续任务按 owner 矩阵逐步采用

## 1. 设计目标

本项目的视觉目标是让“发现群组”像一个安静、可信、可快速浏览的目录：信息层级清晰，卡片有轻微的表面触感，状态表达可预测；管理端则优先保证密度、扫描速度、键盘操作和批量操作的可靠性。

公开端和管理端共用语义 Token、字体层级、焦点规则、状态颜色和基础组件接口，但不强制所有区域使用同一种表面效果。Button、Card、Input、可点击容器和局部状态面板可以使用轻量新拟物；表格、导航、Dialog、下拉和高密度信息区使用扁平或低强度表面。

本规范只服务于 V2 PRD 已冻结的信息架构：顶栏、主搜索、发现新群、标签、自定义板块、所有群组、群组详情、管理群组列表和板块管理。它不改变 API、数据模型、路由、认证或业务状态契约。

## 3. 设计决策等级

- **MUST**：必须遵守。包括深色背景、焦点可见性、状态非颜色表达、原型隔离、语义 Token 和响应式列保留规则。
- **SHOULD**：默认遵守。只有在内容或可访问性验证表明不合适时才调整，并记录原因。
- **MAY**：允许使用。不能把 MAY 规则当作新的业务需求。

本文件的具体颜色、圆角、阴影数值是候选 Token；用户已经确认视觉方向，但尚未完成四轮样例确认，因此不得在后续任务中把候选值表述为最终品牌冻结值。

### 4.1.1 评审后补充：边框与表面层

- **MUST**：Card、Button、Input、Avatar 和可点击 Neumorphism 表面默认使用透明边框，不显示实体细线；Hover、Focus、Pressed、Selected、Error 等状态再使用语义边框或独立焦点环表达变化。
- **MUST**：默认阴影采用紧凑的明暗双向阴影，不能覆盖相邻控件；控件组通过间距、层叠上下文和 hover 提升层级保持清晰。
- **MUST**：Button、Card、Input 默认使用正常 Neumorphism 表面；默认状态不能使用内嵌阴影，只有 Pressed/Selected 才使用 `shadow-pressed`。
- **MUST**：按钮只提供 `normal` 和 `quiet` 两种表面变体；`quiet` 使用浅色文字/透明表面，危险语义通过独立 tone 表达，不新增第三种表面。
- **MUST**：Input 的焦点高亮只紧贴 `proto-field__control`，使用细边框/一层窄 box-shadow；输入元素自身不显示粗 outline 或第二层 focus ring。

### 4.4 阴影和新拟物规则

```css
--shadow-raised: 7px 7px 16px rgba(160,171,187,.27), -7px -7px 16px rgba(255,255,255,.84);
--shadow-hover: 9px 9px 20px rgba(160,171,187,.31), -9px -9px 20px rgba(255,255,255,.92);
--shadow-pressed: inset 4px 4px 9px rgba(166,177,192,.30), inset -4px -4px 9px rgba(255,255,255,.80);
```

深色主题使用单独、低强度的深色映射，避免发白、脏灰和边界消失。管理表格、导航、Dialog、下拉和高密度区域默认无阴影或低强度表面。任何使用阴影的状态都必须再提供边框、背景、文字、图标或语义属性等非阴影信号。

Carousel 滚动容器必须为卡片四周预留足够的滚动内边距，避免阴影/高光被 viewport 裁切；同一 Carousel 的卡片统一采用该组夹具中最长内容所需的高度。公开板块使用 Carousel，Grid 只用于所有群组和搜索结果。

## 5. 字体、布局和响应式

### 5.1 字体层级

优先使用 `Inter, "SF Pro Display", "PingFang SC", "Microsoft YaHei", system-ui, sans-serif`。不引入未审查字体。

- 页面主标题：普通页面使用 `clamp(2.25rem, 4vw, 4.1rem)`，首页 Hero 的 `.hero-copy h1` 最大限制为 48px（`3rem`），行高约 1.03；首页 Hero 使用更紧凑的标题与容器高度。
- Section 标题：约 1.45–2rem，字重 750–800。
- 正文：约 0.92–1.02rem，行高 1.7–1.8。
- 辅助信息：0.7–0.82rem，使用 `text-secondary` 或 `text-muted`。
- 表格和徽标：0.68–0.8rem；数字不依赖颜色传达状态。

长中文、长英文单词和 Emoji 混排必须允许换行、截断或在 Dialog 中完整阅读；卡片简介最多展示四行，详情弹窗展示完整内容。

### 5.2 容器和断点

页面容器最大宽度候选为 1280px；桌面左右内边距至少 24px，手机左右内边距 12–16px。超宽屏保持居中，不把内容拉到不可读的全宽。

按内容临界点而不是设备名称使用以下检查宽度：

| 宽度 | 必须观察 |
| --- | --- |
| 360px | 顶栏操作不溢出；Grid 双列；Dialog 接近全屏；按钮文字可读 |
| 390px | Carousel 至少露出两张卡；卡片标题/简介截断稳定 |
| 768px | 平板双列/三列过渡；管理端中等列隐藏顺序正确 |
| 1024px | 管理侧栏、工具栏和表格仍可扫描 |
| 1280px | 完整桌面布局、七列标签、五列群组 Grid、Carousel 一行五卡和操作区 |
| 1440px | 容器居中、留白稳定、无额外拉伸 |

还必须人工检查 200% 缩放、横屏手机、窄高度、超长中文标题、长英文单词和 Emoji。页面不能出现非预期的页面级横向滚动。

### 5.3 顶栏

宽屏显示 Logo、品牌标题“找一个值得加入的群”、主题按钮、GitHub 支持按钮和“添加新群”。三个顶栏操作统一使用药丸形 Neumorphism；按钮宽度按文案自适应，主题按钮在 system/light/dark 三个状态间保持同一宽度，文字统一为“系统/浅色/深色”；不使用原生 select。窄屏允许主题/GitHub 只显示图标，但核心“添加新群”操作保留文案，不能变成单独加号、汉堡菜单或隐藏。浏览器标签标题也必须是“找一个值得加入的群”，焦点环独立于顶栏表面。

### 5.4 Grid、Carousel、表格和 Dialog

- 手机标准目标为至少两列 Grid；桌面标签卡片固定每行最多七个，桌面群组 Grid 目标为五列；标签按 5/3/2 列、群组按 4/3/2 列响应式降级。标签最多七个字，超长内容必须截断或在编辑时阻止继续输入。
- Carousel 使用横向滚动区，支持鼠标拖动、滚轮/触控板、触摸和键盘焦点；每个断点的卡片宽度必须与对应 Grid 卡片一致。手机至少同时看到两张卡；边界使用叠加透明渐变淡出和箭头表达，不渲染独立 edge hint 节点。卡片主体和 footer 固定为统一高度，简介最多四行；controls 与 section hint 下移约 12px 后仍不得互相遮挡。
- 管理表格响应式隐藏顺序固定为：`标签 → 性质 → 点赞 → 平台`；永久保留 `标题 → 状态 → 操作`。中等宽度展示标题、状态、性质、点赞、平台、操作；窄屏只展示标题、状态、操作，详情进入抽屉/弹窗。所有列标题都是排序按钮，循环无排序/升序/降序；正文操作保持扁平，窄屏合并为扁平三点入口。
- Dialog 桌面居中：详情最大约 640px，公开提交约 680px，管理编辑约 720px；手机底部接近全屏，安全区、内容滚动区和底部操作区分离。Escape、关闭按钮、遮罩点击和焦点归还均需覆盖。编辑 Dialog 必须比详情 Dialog 稍大但不要求同宽。板块详细信息编辑 Dialog 至少覆盖标题、描述、启用状态和成员数摘要；板块管理还必须提供独立的“新增板块” Dialog，复用该表单的创建态。

## 6. 组件规范

### 6.1 Button

提供 `normal`、`quiet` 两种表面，以及 `default`、`danger` 语义 tone 和图标/紧凑尺寸组合。默认、Hover、Pressed、Focus、Disabled、Loading 都必须可见：

- 默认：`normal` 使用轻量外凸表面且默认透明边框；`quiet` 使用浅色文字和透明表面，不制造第三种按钮表面。
- Hover：只轻微抬升或调整阴影，不改变布局。
- Pressed/Selected：可用内嵌阴影，但同时改变背景/边框或 `aria-pressed`。
- Focus：`focus-visible` 高对比 3px 环，不能被裁切。
- Disabled：`disabled` 属性、文字/图标和降低的交互能力共同表达，不只降低透明度。
- Loading：保留按钮尺寸，显示 spinner 和“加载中”可访问名称，禁止重复提交。

### 6.2 Input 和表单控件

使用原生 `input`、`textarea`、`checkbox` 和 `switch` 语义；Select 在原型中使用 Vue 原生 listbox 组件重建，不直接暴露系统下拉外观。每个控件有 label、帮助/错误文字和 `aria-invalid` 需要时的映射。默认 Input 可使用轻量外凸表面；错误状态使用高对比边框和文字；Focus 只显示紧贴控件容器的一层细高亮，输入元素自身不叠加粗 outline 或第二层 focus ring。管理编辑的标题框、添加标签框和公开提交字段必须复用同一层 control 高亮；“添加”按钮保持横向文案不折行。加群方式使用加号图标与“添加加群方式”文案组成的自定义下拉选择“链接/群号/二维码”，每行的“邀请链接/群号/二维码”是不可编辑标签，只有链接/群号内容可编辑。二维码行使用图片上传按钮；已有图片同时展示预览和再次上传按钮，整行使用高于普通加群方式的图片区域。Loading 保持控件宽度稳定。

### 6.3 GroupCard

卡片只展示头像、标题、平台、性质徽标、最多四行简介、最多少量标签和点赞按钮/数量；桌面紧凑布局中头像和标题同一行，标题下一行的 `group-card__meta` 靠左，`proto-badge` 与 `group-card__platform` 在左侧相邻排列；头像表面不使用阴影，透明 Logo 不被高光干扰。不得放加群按钮、群号、二维码或复制按钮。卡片主体是可键盘聚焦的按钮或等价可访问控件，点赞按钮必须阻止事件冒泡，确保点赞不打开详情。

头像必须声明尺寸并提供缺失/加载失败的确定性占位。状态不能只靠颜色。长标题截断规则固定，完整内容在 Dialog 中阅读。

### 6.4 GroupDialog

内容包括头像、完整标题/简介、平台、点赞、多个加群方式、分享、关闭、二维码占位和长内容滚动。二维码原型只能使用明确的模拟占位，不得让用户误以为对应真实群组。Dialog 必须提供 `role=dialog`、`aria-modal`、标题关联、初始焦点、Escape、关闭控件、焦点归还和移动端安全区；打开时仅使用 `opacity` 与 `transform` 实现轻微上浮淡入，并在 `prefers-reduced-motion` 下禁用动效。

### 6.4.1 两个新增群 Dialog

- 顶部“添加新群”只打开公开提交 Dialog，但视觉结构和字段交互复用完整管理编辑表单；包含头像上传、标题、简介、性质、平台（必须包含“微信群”选项）、固定文案的加群方式下拉、群号/HTTPS 邀请链接、二维码图片上传、标签、提交者联系方式和只读“待审核”状态；不得出现可编辑的“状态”控件或“审核备注”字段。底部主按钮文案固定为“提交群组”，提交后关闭并显示“提交成功，等待审核”。
- 管理工作台“添加新群”只打开管理编辑 Dialog：复用 `PrototypeAdminEditForm` 的完整可编辑字段，包括头像操作、标题、简介、性质、平台、状态、标签、加群方式和审核备注；提交只更新样例内存并提示本地结果。
- 两个入口必须使用不同的 Dialog 标识、可关闭、可用键盘操作，且都不得调用真实 API。管理编辑 Dialog 的宽度约 720px，公开提交 Dialog 约 680px，详情 Dialog 约 640px。
- 已有群组的管理编辑 Dialog 底部提供带 danger 语义的“删除群组”按钮；管理创建 Dialog 不显示该按钮。板块管理的成员表在窄屏隐藏“状态”列，将“编辑/移除”合并为无 Neumorphism 的三点按钮；桌面仍保留两个扁平文字操作。
- 头像和二维码照片上传只允许图片类型；原型用本地占位预览表达上传结果，不调用真实存储 API。真实实现必须以单个 IP 或设备为限流主体，同一主体每小时最多成功上传 1 次，超限需要在控件附近说明原因并保留重试路径。不要用 board drag handle 表达排序，板块只提供上移/下移按钮。点击品牌 Logo 必须回到公开根视图并清空搜索词、标签筛选和搜索状态。
- Dialog 遮罩必须使用独立的 opacity 淡入，不能突然出现；桌面 Dialog 可使用轻微 `translateY + scale` 淡入，手机/窄屏底部抽屉只使用 `translateY + opacity`，不得缩放。所有动效只改变 compositor 属性，并在 `prefers-reduced-motion` 下取消。

### 6.5 Tag、Badge、Toast、ErrorBanner、Skeleton 和空状态

- Tag/Badge 的 Selected/Active 除颜色外还需要边框、形状或文字状态。
- Toast 使用 `aria-live`，成功、信息、警告、错误均带图标和文字；移动端不遮挡主要操作。
- ErrorBanner 提供可读错误和可执行的重试/恢复操作；不以全局错误替代独立模块内容。
- Skeleton 在浅色和深色中都与背景有足够层级；`prefers-reduced-motion` 下停止 shimmer。
- 空状态说明当前状态和下一步，不只显示“暂无数据”。

### 6.6 管理端群组表格

表头使用真实 `th` 和可操作排序按钮，状态使用文字徽标，排序图标有 accessible name，操作区桌面保留编辑/删除，窄屏合并为扁平更多入口。群组管理工具栏在状态 Select 与“添加新群”之间提供“显示回收站”开关；四个业务状态“已发布、已下架、待审核、已拒绝”始终由独立 Select 筛选，回收站只控制带回收站标记的数据是否加入当前结果，不得把“已下架”当作回收站别名。开关使用 `aria-pressed` 和 Pressed/Selected 表面表达开启状态。表格以功能优先为原则，无大面积新拟物；只有表头排序按钮可使用轻量 Neumorphism。加载、空、错误、筛选结果为空和窄屏抽屉都要有独立视觉状态。

### 6.8 统计页和完整编辑样例

管理端原型增加固定 Mock 的“运行数据”页：KPI、状态/平台分布、流量趋势、热门群组和系统健康。该页只用于视觉密度与信息层级评审，不调用接口。编辑样例必须覆盖 v1 抽屉的头像、标题、简介、性质、平台、状态、标签、加群方式、私密联系信息和审核备注，并提供未保存提示的视觉状态。

### 6.7 板块管理

每个板块使用清晰标题、说明、启用状态、成员数、上下移、编辑、删除和展开控制，不显示拖拽手柄。成员表固定高度并内部滚动，成员状态可显示已发布和已下架；公开板块不得展示已下架成员。板块顶部提供“新增板块” Dialog；成员表工具栏的“添加新群”打开独立的群组选择 Dialog，只有输入非空搜索词时才渲染匹配结果，结果行只显示迷你头像和群名，并提供本地添加动作。桌面成员表的编辑按钮、窄屏的 `board-member-more` 都打开相同群组编辑 Dialog，但该上下文底部操作为带箭头图标的“移除群组”，不显示“删除群组”；删除垃圾桶语义只保留给群组管理的危险删除操作。待整理板块的 `section-heading__hint` 应与标题基线对齐，不下沉。删除必须先确认，排序只通过上移/下移按钮表达。

## 7. 主题、状态与动效

主题偏好为：

```ts
type ThemePreference = "system" | "light" | "dark";
```

原型使用 `matchMedia("(prefers-color-scheme: dark)")` 跟随系统，不写入正式 localStorage。浅色和深色共用同一语义 Token 名称；深色页面背景始终为深灰 `#15171c` 候选值，禁止 `#000000` 主背景。Skeleton、二维码占位、焦点环、状态徽标和 Dialog 遮罩都要有独立深色映射。

状态优先级：语义属性/文字 > 边框/图标 > 背景 > 阴影。任何 Selected、Disabled、Loading、Error、Success 都不能只靠颜色或阴影。

动效使用 120ms 的快速反馈和 180ms 的普通过渡；Carousel 可平滑滚动，Dialog/Toast 保持简洁。Carousel 两侧渐变挡板只覆盖卡片内容高度，不遮挡 Section heading hint，并继续完全覆盖卡片。`@media (prefers-reduced-motion: reduce)` 下取消滚动动画、shimmer、位移和长过渡，只保留必要的状态切换。
