# 01 全量 Spec 与代码审计技术设计

> 执行前置规则：进入执行或最终批准前，必须完整读取 `docs/PRD/v2/子任务01.md` 原文并逐条核对三份规划；先检查代码、测试、配置、Spec 和任务历史，再与用户按 Trellis Brainstorm 逐轮讨论，每次只问一个最高价值问题。每次用户回答后更新规划；即使无疑问也必须提交最终规划摘要并等待明确批准，未完成前不得实施或修改业务代码。

## 1. 设计目标与联合 Review 修订

本任务的技术产物不是新功能，而是一套可复核的事实审计系统。设计必须让后续 Agent 能从 `research.md` 和 `impact-map.md` 直接知道：当前实现、规范、测试锁定行为、V2 目标、冲突级别、文件所有权、依赖顺序和阻塞条件。

联合 Review 的核心修订：

- 将旧任务元数据映射到当前父任务 `lgqh-v2`，不再引用 `frontend-overhaul` 作为父任务。
- 将旧活动目录 `07-30-frontend-overhaul` 标记为历史/空目录，不作为当前实现证据。
- 将源产品 PRD `docs/PRD/v2/RPD.md`、父 Trellis `prd.md` 和未来审计报告分成三个层次，避免互相覆盖。
- 将“全部 Spec/全部归档任务”改成有清单、有缺失记录、有证据状态的审计对象。
- 将每个领域的事实结论强制绑定到三方证据矩阵和调用链。
- 将 C4/C5 作为后续任务的进入门禁，而不是普通备注。

## 2. 架构与边界

```text
输入证据
  ├─ .trellis/spec + AGENTS.md + workflow
  ├─ 归档 task.json / prd.md / design.md / implement.md
  ├─ docs/PRD/v2/RPD.md + 子任务 PRD
  ├─ src/ + shared/ + functions/ + migrations/
  └─ Vitest / Workers Vitest / Playwright 配置与测试

审计索引
  ├─ 材料清单与缺失项
  ├─ Spec / 代码 / 测试三方矩阵
  ├─ 调用链和数据流证据
  ├─ V2 要求到模块/任务/测试映射
  └─ C0–C5 冲突与风险登记

输出
  ├─ research.md：事实、冲突、复用、修改、风险、API/测试影响
  ├─ impact-map.md：功能、文件、所有权、依赖、风险热力图
  └─ 父任务 PRD 修订建议：事实纠正与可执行边界
```

T01 不拥有业务实现文件，不改变 API、Schema、migration、样式或测试；它拥有审计报告、影响图和有证据的规划修订。

## 3. 证据模型

### 3.1 证据类型

每个结论至少绑定以下一种，重要结论绑定两种以上：

- 文件路径和符号名，必要时附 1-based 行号。
- 测试文件和测试名称。
- migration 文件和表/索引/约束名称。
- route 路径、schema 名称、repository 方法或 service 方法。
- Git 历史任务和对应 commit/归档文档。

不允许使用“应该”“似乎”“当前支持”作为无证据结论。

### 3.2 三方一致性矩阵

每个重点领域使用以下结构：

| 领域 | Spec 规定 | 代码行为 | 测试行为 | 证据 | 一致性结论 | V2 影响 |
| --- | --- | --- | --- | --- | --- | --- |
| 例如搜索 | 规则 | 实际调用链 | 已锁定场景 | 路径/符号/测试 | 一致/偏差/过时 | 保留/修改/决策 |

需要区分：Spec 与代码一致但无测试；Spec 与代码不一致；代码与测试一致但 Spec 过时；三者互相不一致。

### 3.3 调用链模型

公开读路径至少追踪：

```text
前端交互
→ composable / view
→ API client
→ Hono route
→ service
→ repository
→ D1
```

管理写路径至少追踪：

```text
管理端操作
→ 认证和 CSRF
→ route
→ 状态转换/service
→ D1 batch / R2 生命周期
→ 响应
→ 前端状态和测试
```

状态修改、回收站、永久删除、资源清理和并发冲突不得只看一个文件。

## 4. 审计域与边界契约

### 4.1 规范与历史

规范审计输出所有 Spec 路径、领域、约束、V2 关系和一致性状态。历史审计输出不可重新引入的 Bug、迁移约束、设计决策、边界条件和不能轻易删除的复杂逻辑。

旧活动目录 `07-30-frontend-overhaul` 只作为“曾经被引用但当前为空”的差异证据；当前父任务以 `.trellis/tasks/08-01-lgqh-v2` 和其 `task.json` 为准。

### 4.2 公开端与搜索

审计必须覆盖 HomeView、路由、GroupList/GroupCard、提交/QR/剪贴板/点赞、加载/空/错误、响应式、搜索输入、debounce、IME、URL、历史、字段、排序、cursor、重复、取消、无限滚动和测试。

结论必须回答：V2 的首页区域能否复用现有状态流；公开目录的旋转排序和 cursor 能否继续；搜索是否可以在不改变匹配语义的情况下接入新首页模式；详情深链接是否会改变公开过滤。

### 4.3 旋转排序与发现新群

把两个规则分开建模：

- 现有目录/搜索旋转排序：核对 epoch、时区、槽位、循环移位、稳定字段和 cursor 耦合。
- V2 发现新群：核对 `last_published_at` 状态转换、`published` 过滤、`DESC + id` 稳定排序和最多 10 条。

如果两者共享 repository/service，必须在影响图中标出高冲突文件；不得因新增发现查询删除或改变现有固定时间测试。

### 4.4 管理分页

将管理 keyset 与公开 cursor 作为两种不同契约审计。输出必须列明：当前 cursor 结构、页码接口变化、固定 50 条、total count、排序稳定性、URL 参数、删除退页和 OFFSET 风险。不得把管理端页码要求扩散为公开端页码。

### 4.5 状态机、回收站与 R2

先列出代码真实状态集合和转换入口，再映射 V2 的 `last_published_at` 与板块关联规则。特别检查：

- 非已发布 → 已发布的所有入口。
- 已发布 → 已下架是否保留时间和关联。
- 移入回收站的 D1/关联原子边界。
- 恢复后不恢复板块关联。
- 永久删除的 D1 batch、资源收集、R2 清理和失败恢复。
- 外键级联是否会与显式删除重复或冲突。

### 4.6 主题、测试和 migration

主题只审计，不实现；记录 CSS Token、Tailwind `darkMode`、挂载时机、localStorage、系统检测和公共状态组件的实际来源。

Playwright 审计记录浏览器矩阵、数据初始化、管理员登录、D1 环境、移动 viewport、WebKit、截图、时间、剪贴板、拖拽/触摸和选择器稳定性。

Migration 审计记录编号、建表、时间类型、外键、索引、默认数据、幂等、本地/测试迁移、部署顺序和历史 migration 修改策略；只提出方案，不创建 migration。

## 5. 冲突分类与决策门禁

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| C0 | 现有实现可复用，V2 无冲突 | 记录证据，允许后续复用 |
| C1 | 文档字段/术语/现状偏差 | 依据证据修订 PRD并记录原因 |
| C2 | 产品目标兼容但需要扩展/替换 | 补充技术约束，交后续设计/实现 |
| C3 | 跨领域机制冲突 | 修订依赖、所有权、迁移顺序并标高风险 |
| C4 | 证据无法唯一决定产品行为 | 列选项、影响、推荐，等待用户决策 |
| C5 | 可能造成数据损坏、泄露、资源破坏、不可逆迁移、安全绕过或无替代测试 | 阻塞相关后续任务，先完成决策 |

C4/C5 不得被改写成普通“待优化项”。只有可以由仓库证据解决的问题才应在审计中直接解决，不把可读代码问题抛给用户。

## 6. 交付物设计

### 6.1 `research.md`

必须按以下结构组织：

1. 执行摘要：架构评价、V2 可行性、可复用能力、最大风险、阻塞数量、PRD 调整方向。
2. 已阅读材料清单：Spec、归档任务、父任务、核心代码、migration、测试；缺失材料单列。
3. 当前实现事实：首页、卡片/详情、搜索、cursor、旋转、点赞、管理列表/keyset、状态机、回收站、永久删除、图片/R2、主题、测试、migration。
4. Spec/代码一致性三方矩阵。
5. V2 冲突表：编号、级别、PRD 原规则、当前事实、证据、风险、建议、是否需决策。
6. 可复用模块：路径、职责、复用方式、扩展、不可破坏行为、测试。
7. 必须修改模块：路径、原因、类型、后续任务、依赖、风险。
8. 数据迁移风险：字段、默认板块、外键/级联、索引、部署、旧代码、测试库、回滚和数据量。
9. API 影响面：公开/管理 API、共享 Contract、Typed fetch、错误、分页、认证/CSRF、冲突和时间行为。
10. 测试影响面：保留、修改、删除/替代、新增 Vitest/Workers/E2E、视觉、时间和夹具。
11. 未决问题：只保留无法从仓库唯一得出的 C4/C5 问题。

### 6.2 `impact-map.md`

必须包含：

- 功能到前端、后端、数据库、共享 Contract、测试的映射。
- 新增、修改、可能修改、不应修改和高冲突共享文件清单。
- 高冲突文件的唯一拥有子任务与其他任务的接入接口。
- 子任务依赖图、可并行/必须串行、Contract/视觉/migration 门禁。
- 低/中/高/阻塞风险热力图，至少覆盖数据一致性、安全、状态机、API 兼容、UI 回归、响应式、无障碍、测试稳定性和部署迁移。

功能映射至少覆盖主题、顶栏、卡片、详情、分享、Carousel、发现、标签、板块、目录、搜索、管理分页、响应式表格和回收站关联清理。

### 6.3 总 PRD 修订建议

每项修改必须标为：事实纠正、术语纠正、约束补充、验收补充、测试补充、任务边界、依赖、风险或待用户决策，并包含：位置、原内容、新内容、原因、证据和冲突等级。

不得降低已冻结方向：Grid/Carousel 分工、已下架隔离、发现新群发布时间、详情弹窗、`?group=`、规范分享链接、卡片四行、板块可为零、默认板块可删除、未启用可编辑、可添加已下架群、回收站清理关联、固定高度成员表、管理每页 50 条、公开 cursor、三态主题和手机至少两张 Carousel 卡片。

## 7. 跨任务所有权与后续影响

T01 只拥有审计报告、影响图和规划修订建议，不拥有业务实现文件。影响图必须为 T02–T10 标明实际文件所有权，尤其是：

- 共享 domain、Zod Schema、DTO 和 API client。
- groups migration、状态转换、repository 过滤和回收站清理。
- 全局 CSS/Token、主题入口、顶栏和公共状态组件。
- 首页容器、搜索 composable、URL state、GroupCard、详情和 Carousel。
- 管理导航、表格、抽屉、分页 query state 和板块页面。
- Playwright fixtures、固定时间工具、Workers 数据库初始化。

若多个后续任务触碰同一文件，必须在影响图中给出合并顺序和接口边界，禁止并行大范围覆盖。
