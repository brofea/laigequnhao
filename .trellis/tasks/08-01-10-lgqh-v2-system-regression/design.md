# T10 系统回归、无障碍与发布验收：设计规划

> 执行前置规则：进入执行或最终批准前，必须完整读取 `docs/PRD/v2/子任务10.md` 原文并逐条核对三份规划；先检查代码、测试、配置、Spec 和任务历史，再与用户按 Trellis Brainstorm 逐轮讨论，每次只问一个最高价值问题。每次用户回答后更新规划；即使无疑问也必须提交最终规划摘要并等待明确批准，未完成前不得实施或修改业务代码。

## 1. 设计结论

T10 采用“冻结候选版本 → 建立隔离数据 → 自动化分层回归 → 人工可用性验收 → 性能与迁移演练 → 最小跨任务修复 → 重跑闸门 → 形成验收文档”的证据链。

本任务是发布验证层，不是新的业务实现层。任何发现都先归类到原任务、共享 Contract、测试基础设施或发布配置；只有跨任务集成阻塞问题才允许在 T10 做最小修复。

设计必须保留以下边界：

- 产品规则来自冻结 V2 PRD、子任务 PRD、已确认 UI 设计和正式 Spec。
- 自动化测试、人工检查、视觉基线和 migration 演练分别保留证据，不以一种证据替代另一种。
- 所有测试数据、时钟、随机种子、浏览器、字体、locale 和主题均可复现。
- 所有发布结论都由 S0/S1/S2 闸门和必需测试结果共同决定。
- T10 规划完成不代表功能已经验收通过。

## 2. 当前仓库证据与执行约束

当前仓库已识别到：

- `package.json` 提供 `typecheck`、`lint`、`format:check`、`build`、`test`、`test:workers`、`test:e2e`。
- `package.json` 提供 `db:test:migrate`、`db:test:reset`、`db:test:unlock` 等测试数据库脚本。
- `vitest.config.ts` 覆盖 `src` 与 `shared` 的 jsdom 测试。
- `vitest.workers.config.ts` 和 `tests/workers` 承担 Workers、D1、迁移和 API 测试。
- `playwright.config.ts` 当前已有 Chromium 桌面和 Chromium 手机项目，配置为单 worker、非 fully parallel。
- `wrangler.jsonc` 包含本地、preview、production 的 D1/R2 和环境变量声明；密钥只能通过 secret 配置，不写入验收文档。
- `migrations/` 当前已有历史 migration；T10 不得修改历史文件，只能验证或提出经批准的前向 migration。

执行时要重新确认以上路径和脚本是否仍然有效。规划中的命令不能替代项目真实命令，也不能凭空写入不存在的 Firefox/WebKit 脚本。

## 3. 验收拓扑

### 3.1 本地静态与前端测试层

- Node、包管理器和 lockfile 固定。
- Vue、共享 Contract、浏览器组件使用 jsdom/Vitest。
- 所有 fake timer、matchMedia、localStorage、事件监听器和 AbortController 在测试后清理。
- 前端测试不访问真实生产 D1/R2。

### 3.2 Workers 与 D1 层

- 使用测试专用 Wrangler 配置和测试 D1。
- 认证、CSRF、公开投影、管理接口、迁移和资源生命周期各自有可隔离 fixture。
- 迁移测试数据库与业务测试数据库不能共享不可预测状态。
- 每个套件在开始前建立数据，在结束后清理或销毁。

### 3.3 Playwright 集成层

- 前端 dev server 与测试 API server 分开启动。
- 每一轮测试使用固定数据快照和测试账号。
- 公开端和管理端通过真实路由访问，不用组件内部 mock 代替集成行为。
- Chromium、Firefox、WebKit 项目明确记录浏览器版本、视口、主题、locale 和时区。
- CI 并行模式和单 worker 模式都必须至少验证一次。

### 3.4 发布候选层

- 候选 Commit 冻结后才建立正式截图基线和发布演练结果。
- preview 等效生产环境用于配置、缓存、canonical origin、D1/R2 binding 和冒烟。
- production 只在授权、备份和明确发布窗口内执行，不在规划阶段执行。

## 4. 数据策略

### 4.1 最小完整数据集

数据工厂必须支持以下 fixture：

- 0 个群组。
- 1 个群组。
- 49、50、51、100 以及多页群组。
- 已发布、已下架、回收站三种状态。
- 相同发布时间、点赞数、标题和创建时间。
- 中文、英文、Emoji、ZWJ、组合字符和全角字符。
- 标题宽度 50、51，简介宽度 1000、1001。
- 多标签、多加入方式、二维码、损坏图片和缺图。
- 0 个板块、1 个空板块、多个板块、未启用板块。
- 仅含已下架成员的板块。
- 具有手动正序、手动倒序和每小时随机模式的板块。
- 成员数量较多、重复候选、跨板块重复引用的数据。
- 搜索有结果、无结果、快速输入和错误重试数据。
- Analytics 有数据、空数据和故障数据。

### 4.2 时间和随机策略

- 所有时间相关测试使用固定时钟或注入的测试时间。
- 每小时随机测试固定时区、小时槽位、哈希输入和稳定次排序。
- 不用真实当前时间判断截图或排序。
- 不用 `Math.random()` 产生验收数据。
- 数据 fixture 的创建顺序不能决定业务排序结果。

### 4.3 隔离和生命周期

- `beforeEach` 或等效 fixture 负责建立最小数据。
- 测试结束后删除临时记录、localStorage、cookies、文件和上传资源。
- 并行 worker 通过独立命名空间、数据库或数据前缀隔离。
- 迁移演练从空库和 `0001`–`0003` schema 快照分别开始。
- 测试重复执行得到同样的条数、排序、响应和截图结构。

### 5.1 浏览器矩阵

- 自动主题且系统浅色。
- 自动主题且系统深色。

### 5.4 状态矩阵

- 初始加载。
- 局部 loading。
- 空结果。
- 业务错误。
- 网络错误。
- 重试中。
- 权限错误。
- 会话过期。

- 禁用板块。
- 公开数据被过滤。
- 删除、恢复和分页退页。

## 6. 公开端验收设计

### 6.1 首页和搜索

- 首屏区域顺序是 Header、Search、Discover New Groups、All Tags、Dynamic Boards、All Groups。
- 有效 trim 后的 `q` 非空时只进入搜索模式，清空后恢复默认首页。
- `q` 与 `group` 可共存，刷新、后退、前进和直接深链接一致。
- Discover 只取最近 10 个已发布群组，不因普通编辑重新进入前列。
- Tags 只聚合已发布群组，区域错误不阻断其他区域。
- All Groups 和 Search 使用 cursor，跨页无重复、无遗漏且请求竞态安全。

### 6.2 卡片、Carousel 和 Dialog

- GroupCard 字段、两行标题、四行简介、点赞独立操作和不显示加群按钮符合 T06。
- Carousel 只有确有可滚动内容时拦截输入；到边界允许页面继续滚动。
- 鼠标拖动、触摸、触控板、滚轮和键盘行为不得互相误触。
- Dialog 从卡片、深链接和浏览器历史进入/退出一致。
- Dialog 使用焦点陷阱、背景滚动锁定、焦点恢复、二维码二级层和移动端动态视口。
- 分享只复制 canonical origin 与 `group`，不复制 `q`、管理参数、会话或密钥。

### 6.3 业务与安全

- 点赞在卡片、Dialog、板块、搜索和默认首页同步，失败时精确回滚。
- 群组提交保留标题/简介显示宽度、Turnstile、图片、标签和加入方式能力。
- 下架和回收站群组不会出现在公开首页、搜索、板块、详情或分享深链接。
- 公开接口不返回内部 token、设备哈希、管理字段、R2 key 或敏感加入信息。

## 7. 管理端验收设计

### 7.1 导航和群组

- 群组、板块、Analytics 三页面有直接访问、刷新、后退、前进、当前项高亮和 `aria-current`。
- 群组列表固定每页 50 条，COUNT 与 items 过滤条件完全一致。
- page、q、status、trash、sort、direction URL 状态可复制、刷新和历史恢复。
- 过滤或排序变化回到第 1 页；当前页最后一条被删除后规范化到上一有效页。
- 稳定排序包含唯一 ID tie-break，不因并发或重复主字段产生遗漏。

### 7.2 响应式表格和抽屉

- Tags → Property → Likes → Platform 按顺序隐藏。
- Title、Status、Actions 在所有支持宽度始终保留。
- 360px 无页面级横向溢出，操作菜单仍完整。
- 手机新建/编辑抽屉接近全屏，底部操作避开安全区和软键盘。
- 脏表单关闭有守卫，成功/失败/取消后焦点回到触发控件。
- 图片、标签、加入方式、版本冲突和既有群组能力无回归。

### 7.3 板块和成员

- 板块 CRUD、启用/关闭、排序模式、空板块、零板块和默认板块规则一致。
- 板块拖拽只负责板块顺序，不误触成员拖拽；键盘/移动端有明确后备。
- 成员表固定高度、内部滚动、标题/状态/操作语义完整。
- 添加已发布/已下架候选、重复防护、编辑、移动、上移、下移、移除和计数一致。
- 版本冲突不静默覆盖，失败的乐观操作恢复源和目标状态。

## 8. 数据、API 和部署验收设计

- Shared Contract 在前端、Functions、Workers 测试和文档中只有一个语义来源。
- 管理写入均经认证、CSRF、Schema、白名单和 mutation token 校验。
- `last_published_at` 只在新发布或重新发布时正确更新，普通编辑不更新。
- 公开板块使用启用板块、已发布成员、位置/模式和稳定随机规则。
- 回收站进入时原子清理板块关联，恢复不自动重挂，永久删除不误删共享资源。
- 管理 COUNT、OFFSET、排序和公共 cursor 查询互不改变对方语义。
- canonical origin、缓存键、失效时机和公开/管理缓存范围有证据。
- D1/R2/Analytics/Turnstile/会话/CSRF 配置只验证存在和来源，不记录密钥值。

## 9. 无障碍与视觉设计

- 键盘从顶栏、搜索、标签、Carousel、卡片、Dialog、分享、表单和管理端完成核心流程。
- Dialog、QR、抽屉、确认层和 Toast 的焦点、层级、滚动锁定和恢复可观察。
- 搜索、Carousel、Dialog、分页、表格、导航、状态、错误和加载使用正确语义。
- 图标按钮有名称，状态不只依赖颜色，排序状态有 `aria-sort`，分页有当前页语义。
- 200% 缩放不隐藏核心操作；减少动效不依赖动画结束事件。
- 浅色、深色、焦点环、危险按钮、禁用态、表头、Toast、Skeleton 和图表均可读。
- 基线截图使用固定数据和环境，差异分类为设计变化、浏览器差异、内容变化、布局回归或不稳定。

## 10. 性能和稳定性设计

- 检查首页首屏请求、板块成员请求、标签聚合、Discover、All Groups、Search、管理 COUNT 和 OFFSET。
- 确认板块不会每个成员请求一次，卡片不会逐张请求详情，管理页不会超过固定 50 行。
- Dialog 和二维码按需加载，图片懒加载，页面切换取消或忽略旧请求。
- 重复打开关闭 Dialog/抽屉、切换搜索/页面/窗口尺寸，监听器、Observer、fake timer 和 body lock 不累计。
- 记录数据规模、请求数、关键响应时间、DOM 规模、内存观察和风险结论。
- 关键 Playwright 套件至少连续通过两次，识别时间、动画、随机、缓存和并行污染。

## 11. migration 演练设计

演练分为四条独立路径：

1. 空库初始化：应用全部 migration，验证旧表、字段、索引、外键、默认板块和应用启动。
2. 当前 schema 升级：装载 `0001`–`0003` schema，验证现有数据保留、`last_published_at` 全部为 `NULL`、板块表/关联表和默认板块。
3. Seed 宽度：验证 seed 合法、超限输入拒绝且不静默截断。
4. 失败与部署顺序：模拟中断、索引失败、新增字段/表失败、旧代码先运行和新代码先运行的边界。

每条路径都记录初始 schema、数据规模、实际命令、结果、失败症状、恢复方法、是否需要前向修复和最终批准人。

## 12. 问题分类和修复设计

问题记录字段固定为：

- ID。
- 发现阶段和浏览器/视口。
- 影响任务。
- 严重级别。
- 前置数据和复现步骤。
- 预期与实际。
- 根因类别。
- 最小修复边界。
- 自动化回归测试。
- 局部复测和全量关键套件结果。
- 视觉基线是否更新及原因。
- 最终状态、责任归属和延期批准。

允许的根因类别：

- Contract 不一致。
- 路由 query/历史不一致。
- 请求竞态或取消不完整。
- CSS Token、z-index 或响应式整合冲突。
- 焦点、ARIA 或滚动锁定整合冲突。
- 缓存失效或公开投影错误。
- 测试 fixture、时间、随机或并行隔离问题。
- migration 部署兼容问题。
- 配置、binding 或 canonical origin 错误。

需要退回原任务或总任务的类别：

- 产品规则、状态机、排序、分页、字段或信息架构变化。
- 新领域模型、新 API 语义、新角色或大规模重构。
- 修改历史 migration 或永久改变数据策略。

## 13. `acceptance.md` 设计

未来实施阶段创建的 `acceptance.md` 至少包含：

- 元信息：任务、候选 Commit、分支、日期、环境、负责人、结论。
- T01–T09 依赖状态和已知问题。
- Node、包管理器、Wrangler、浏览器、OS、时区、locale、D1、R2。
- 每条实际命令、退出码、测试数量、失败和修复。
- 功能验收矩阵：验收项、结果、自动化证据、人工检查、问题 ID。
- 无障碍、浏览器、视口、主题、性能、migration 和缓存结果。
- 视觉截图目录、差异分类、基线更新原因。
- 每个问题的完整修复记录。
- 未解决问题、延期批准和后续任务。
- 发布配置、备份、migration、部署、冒烟、观察和前向修复。
- 只能写“通过，可以发布”或“未通过，禁止发布”的最终结论。

## 14. 关键风险和缓解

- 依赖任务仍在 planning：先阻塞 T10，禁止伪造集成证据。
- Playwright 浏览器项目不足：补齐配置/执行来源，不能把 Chromium 结果冒充 WebKit。
- 测试数据相互污染：增加 fixture namespace、独立数据库或严格清理并验证重复执行。
- 迁移不可逆：先做脱敏副本、备份演练和旧代码兼容验证。
- 视觉差异不稳定：固定时钟、字体、动画、数据、浏览器和 locale。
- 隐藏数据泄露：直接检查公开响应字段、缓存和深链接，不只检查页面文本。
- 修复范围膨胀：每个修复绑定一个问题 ID 和原任务边界，超出即退回。
- “全部通过”被过早填写：`acceptance.md` 只能在实际命令和人工检查完成后更新。
