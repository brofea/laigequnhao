# 完善 admin 页面功能

## 目标与用户价值

把 admin 群组管理页从基础列表和有限编辑能力，完善为可以高效定位记录、稳定排序，并完整维护群组及其关联数据的管理工具；同时统一主页与管理端搜索语义，补齐二维码加群方式从上传、编辑到公开使用和安全清理的闭环。

## 当前收敛阶段

三个实现子任务已经完成，当前不再扩展产品能力，只修复最终集成验收暴露出的三个根问题：

1. **聚合更新必须使用真正唯一的写入令牌。** 现有单 batch 方向保留，但不得继续把毫秒级 `updated_at` 当作请求唯一标识。两个携带相同旧版本、在同一毫秒进入的请求中，只允许一个请求修改 `groups`、标签、加群方式、审核备注和 asset 引用。
2. **管理员必须能查看已有二维码。** 管理 API 已能返回 `assetUrl`/`qrCodeUrl`，该 URL 必须完整传递到抽屉草稿，并在没有本地 Object URL 时作为二维码预览回退。
3. **验收必须证明真实行为。** 不再以测试数量或固定 UUID 的 401/404 作为资源生命周期证明；必须创建真实 staged/ready asset、真实群组引用和可控 R2 失败，并断言 D1、R2、HTTP 与 UI 的最终状态。

本阶段采用单 Agent 串行实现，禁止再次拆成多个并行补丁。实现前先补失败测试；测试不能证明的行为不视为完成。

## 背景与仓库事实

- 群组业务状态固定为 `pending`、`published`、`rejected`、`delisted`；软删除由独立的 `deleted_at` 表示，不是第五种业务状态（`migrations/0001_initial.sql:12`，`.trellis/tasks/archive/2026-07/00-bootstrap-guidelines/prd.md:54-57,98`）。
- `group_tags`、`join_methods`、`submission_details` 已通过 `group_id` 外键关联 `groups`（`migrations/0001_initial.sql:34-66`）。
- 管理员 DTO 已返回标签、加群方式、提交者联系方式和审核备注，但现有 `PATCH` 只更新 `groups` 主表字段（`shared/contracts/group.ts:26-52`，`functions/_lib/repositories/group-repository.ts:391-417`）。
- 现有管理员列表只支持单个状态和回收站条件，固定按创建时间倒序，前端只读取前 50 条（`functions/_lib/routes/admin-groups.ts:15-31`，`functions/_lib/repositories/group-repository.ts:302-333`）。
- 现有表格只有标题、性质、状态、平台、点赞和操作列，列标题不能排序；现有表单只编辑标题、简介、性质、平台和状态（`src/features/admin/components/AdminGroupTable.vue:38-61`，`src/features/admin/components/AdminGroupForm.vue:16-42`）。
- 主页目前输入即搜索，但只搜索标题和标签；页面已经创建 `AbortController`，API 客户端尚未实际接收其 `signal`（`src/views/HomeView.vue:54-59`，`src/features/groups/composables/useGroupDirectory.ts:16-20`，`src/features/groups/api.ts:37`）。
- 资源上传路由会写入 `assets`，但现有 migration 没有创建该表，也没有二维码资源与 `join_methods` 的可靠引用关系（`functions/_lib/routes/admin-assets.ts:92`，`migrations/0001_initial.sql:6-74`）。
- 主页已经渲染二维码按钮文案，但点击分支只处理群号和 URL，二维码没有实际交互（`src/features/groups/components/GroupCard.vue:97-113`）。
- 上一轮修复要求编辑、删除和恢复成功后就地更新列表，避免全量重载导致滚动跳顶；本任务必须保留该体验。

## 交付范围与子任务

当前任务是规划与最终集成父任务，实际实现拆为三个可独立验收的子任务：

| 子任务 | 交付边界 |
|---|---|
| `07-28-admin-list-search-sort` | 统一主页/管理端搜索；管理端多状态筛选、标签列、全局排序、完整结果遍历和 URL 状态 |
| `07-28-admin-group-aggregate-editor` | 群组主表、标签、文本加群方式、审核备注的原子 CRUD；响应式右侧编辑抽屉 |
| `07-28-qr-resource-public-flow` | 二维码资源 migration、上传关联、替换删除、可重试清理、移除公开开关和主页二维码交互 |

父任务负责共享契约对齐、子任务依赖顺序、全量测试和最终集成 Review，不直接作为实现目标。

## 产品需求

### REQ-FILTER：多状态与回收站筛选

- 顶栏提供五个状态按钮：待审核、已发布、已拒绝、已下架、回收站。
- 首次进入时四个业务状态全部启用、回收站关闭，展示全部未删除记录。
- 四个业务状态可以组合筛选，但正常列表模式下始终至少保留一个；关闭最后一个状态的操作不生效。
- 启用回收站时关闭四个业务状态；退出回收站时恢复进入前的状态组合。
- 回收站记录不可直接编辑，只能查看摘要、恢复或二次确认后永久删除；需要修改时必须先恢复。
- 状态组合和回收站模式写入 URL，刷新、前进和后退后保持一致。

### REQ-SEARCH：统一的模糊搜索

- 管理端搜索框位于筛选按钮与表格之间。
- 主页和管理端都只搜索标题、简介和标签；平台、群号、URL、联系方式、UUID、审核备注和内部元数据不参与搜索。
- “模糊搜索”定义为子串包含匹配：去除输入首尾空白，拉丁字母不区分大小写，中文按原文子串匹配。
- 不提供错别字纠正、拼音匹配、同义词扩展或相似度排序。
- 管理端搜索与当前状态/回收站条件共同生效；主页搜索继续遵循公开可见性与轮换规则。
- 普通输入约 300ms 防抖，回车和清空立即执行；新查询必须取消旧请求或忽略其过期结果。
- 搜索词写入 URL，清空后恢复当前筛选下的完整结果。

### REQ-TABLE：标签列与完整结果集排序

- 表格数据列为标题、性质、状态、平台、标签、点赞；操作列只承载命令，不参与排序。
- 六个数据列的标题均可点击，明确展示升序/降序状态，并提供键盘操作与 `aria-sort`。
- 排序作用于筛选和搜索后的完整结果集，由服务端执行；不得只重排当前已加载记录。
- 默认保持创建时间倒序；点击某一数据列后在升序和降序之间切换，并使用稳定的次级键避免跨页重复或遗漏。
- 标签列按保存顺序展示；标签排序使用规划中定义的稳定标签排序键。
- 管理员可以遍历全部命中记录，不能因当前 50 条读取上限而永久看不到后续数据。
- 编辑、删除、恢复后按当前查询条件就地更新或精确补取，不能无条件全量刷新并把页面滚动到顶部。

### REQ-CRUD：群组聚合数据的完整管理

- 新建和编辑都使用同一个响应式右侧抽屉。
- 宽屏下抽屉保留背后的表格和滚动位置；视口变窄时向左扩展，最终占满全屏。
- 抽屉按基本信息、标签、加群方式、私有信息分区，底部固定取消和保存。
- 有未保存修改时，遮罩、关闭按钮、Escape 或导航关闭必须先确认。
- 基本信息支持标题、简介、性质、平台和业务状态的新增、查看和修改。
- 标签允许 0–5 个，去除首尾空白，空标签和不区分大小写的重复标签不得保存；保存顺序即展示顺序，并提供可访问的调整顺序方式。
- 加群方式允许任意多个，但所有业务状态下至少保留一个。
- 加群方式类型只能是所选平台 `allowedJoinMethods` 允许的 `group_number`、`url`、`qr_code`；同一类型可有多条，但完全重复的值不得保存。
- 群号必须是非空纯文本；URL 必须是合法 `https:`；二维码必须引用已验证的 WebP 资源。
- 切换平台后，不兼容的既有加群方式必须被明确标出并阻止保存，不能静默删除。
- 加群方式和标签的新增、修改、删除、排序先保留在草稿中，只在整体保存时与群组主表原子提交。
- 提交者联系方式只读展示，空值显示“未提供”；审核备注允许编辑。
- 每次编辑携带最后观察到的 `version`；冲突返回 `VERSION_CONFLICT`，重新获取权威数据并要求管理员 Review，禁止静默覆盖。
- 软删除保留原业务状态；恢复后回到该状态；永久删除只允许作用于软删除记录并必须二次确认。

### REQ-QR：二维码资源和公开交互闭环

- 二维码加群方式支持上传、预览、新增、替换和删除；输入 JPG、PNG 或 WebP，浏览器转换为最终 WebP，服务端再次验证签名、尺寸和 300 KB 上限。
- D1 必须保存可验证的二维码资源引用，不能依赖从 URL 猜测 R2 key。
- 新资源先上传并暂存，群组保存成功后才成为正式引用；取消编辑、替换失败或保存失败时不得误删仍被引用的旧资源。
- 替换、删除、软删除后的永久清理必须检查引用；不再使用的 R2 对象和 D1 资源记录需要安全清理。
- R2 与 D1 部分失败时保留可重试状态，不得报告完全成功；“对象已经不存在”按幂等清理成功处理。
- 删除 `qrCodePublic` 配置、schema、条件分支和测试；二维码与群号、URL 一样始终是公开加群方式。
- 主页二维码按钮打开可访问的二维码查看界面，显示所属群名称、二维码图片和明确关闭操作；不得向公开 DTO 泄漏 R2 key 或内部 asset ID。

## 跨层约束

- HTTP 请求体、query 和响应都使用共享 Zod schema；不得继续用 `adminGroupDtoSchema.partial()` 作为写入契约。
- 平台配置、状态枚举、加群方式枚举、搜索归一化和排序 key 必须各有单一事实来源。
- 群组主表、标签、加群方式和审核备注使用 D1 batch/transaction 语义原子写入。
- 管理员响应继续 `no-store`，所有不安全请求继续要求有效会话、同源和 `X-CSRF-Token`。
- 联系方式、审核备注、删除元数据、R2 key、asset ID 和 `version` 不得进入公开 DTO。
- 不修改已经应用的 `0001_initial.sql`；数据库结构变化使用新的有序 migration，并覆盖旧 schema 升级。

## 不在范围

- 除搜索字段统一和二维码公开查看外的主页视觉或交互改版。
- 多管理员、角色、操作审计历史和找回密码。
- 拼音、同义词、错别字容忍、FTS 或外部搜索服务。
- 在线编辑站点平台配置。
- 批量编辑、批量删除、导入导出和跨群复制加群方式。
- 直接编辑回收站记录。

## 验收标准

- `AC-01`：首次进入管理页时四个业务状态全选；可以组合筛选但不能关闭最后一个；回收站与业务状态互斥并能恢复先前组合。
- `AC-02`：回收站没有编辑入口；恢复后记录回到原业务状态并可正常编辑。
- `AC-03`：主页与管理端对标题、简介、标签使用同一子串匹配规则；清空搜索恢复完整结果。
- `AC-04`：快速连续输入不会出现旧响应覆盖新结果；回车和清空立即生效；URL 可恢复查询状态。
- `AC-05`：标题、性质、状态、平台、标签、点赞六列均支持可访问的升降序排序，操作列不排序。
- `AC-06`：排序覆盖完整命中集；跨页或继续加载时顺序稳定，无重复、遗漏或“仅当前页有序”。
- `AC-07`：标签列按保存顺序正确展示，0 个和 5 个标签均可保存，空值、第 6 个和重复标签被拒绝。
- `AC-08`：管理员可创建群组，也可在抽屉中正确回显并修改主表字段、标签、加群方式和审核备注。
- `AC-09`：抽屉在宽屏从右侧展示、窄屏占满全屏；关闭后列表状态和滚动位置不丢失；未保存草稿不会被直接丢弃。
- `AC-10`：所有状态至少有一个平台兼容的加群方式；空数组、非法类型、空群号、非 HTTPS URL、无效二维码和切换平台后的不兼容项均被拒绝。
- `AC-11`：多个同类型加群方式可保存、排序和删除；完全重复项被拒绝；删除最后一项不能保存。
- `AC-12`：联系方式正确回显且只读，空值显示“未提供”；审核备注可编辑且不进入公开 API。
- `AC-13`：聚合保存要么全部成功，要么全部失败；版本冲突不会覆盖新数据，字段错误保留安全草稿。
- `AC-14`：二维码可以上传、预览、替换、删除并通过主页查看；公开响应不包含 R2 key 或 asset ID。
- `AC-15`：`qrCodePublic` 被完整移除，二维码始终参与公开加群方式和“至少一个”不变量。
- `AC-16`：二维码取消、替换、永久删除及失败重试不会产生可证明的误删；孤立资源可以安全回收。
- `AC-17`：软删除、恢复和永久删除保持现有业务状态语义；永久删除仅作用于回收站记录并清理关联数据。
- `AC-18`：编辑、删除和恢复后不发生无条件全量重载造成的滚动跳顶。
- `AC-19`：共享契约、migration、Worker 集成测试、Vue 组件测试和 Playwright 关键路径覆盖上述行为。
- `AC-20`：`pnpm lint`、`pnpm format:check`、`pnpm typecheck`、`pnpm test`、`pnpm test:workers`、`pnpm test:e2e`、`pnpm build` 全部通过。

## 收敛修复验收标准

- `AC-S01`：新增有序 migration 为 `groups` 增加可空 `mutation_token`；不得修改已经应用的 `0001` 或 `0002`。
- `AC-S02`：每次 PATCH 生成 `crypto.randomUUID()` token；主表条件 UPDATE、asset 引用对账、标签/加群方式替换、审核备注 upsert 和 token 清除位于同一个 D1 batch。
- `AC-S03`：所有关联语句只在本次 token 匹配时执行；过期请求即使与成功请求同毫秒生成，也不得修改任何关联表或 asset 引用。
- `AC-S04`：是否发生版本冲突以 batch 第一条条件 UPDATE 的 `meta.changes` 为准，不得通过提交后的 SELECT 推断本请求是否成功。
- `AC-S05`：batch 任一语句失败时，主表、关联表、asset 引用和 token 全部回滚；接口返回安全错误，前端保留草稿。
- `AC-S06`：管理员列表和单条查询返回 ready QR 的可用 `assetUrl`/`qrCodeUrl`；公开响应仍不包含 asset ID、R2 key、version 或私有字段。
- `AC-S07`：`DraftJoinMethod` 保存远端二维码 URL；编辑器优先使用本次上传的 Object URL，否则显示远端 URL。移除或替换 asset 时同步清空旧远端 URL。
- `AC-S08`：删除整条本次上传的二维码方式、点击二维码“移除”、取消抽屉三条路径都请求 purge；已有 ready asset 不被前端 purge，保存后由服务端引用对账处理。
- `AC-S09`：真实 Worker 测试覆盖 staged purge 成功、ready purge 拒绝、引用保护、staged→ready、ready 引用增加/归零、R2 失败进入 `delete_failed`、cleanup 重试和带 QR 永久删除。
- `AC-S10`：并发回归测试固定相同时间戳并提交相同旧版本，证明只有一个 mutation token 获胜且失败请求关联操作为零副作用。
- `AC-S11`：Vue 测试覆盖已有二维码远端预览、本地预览优先、删除整行触发 cleanup、ready asset 不被误 purge。
- `AC-S12`：Playwright 至少覆盖“管理员打开已有 QR 群组并看到二维码”和“上传 QR→保存→主页查看”两条关键路径；使用隔离的 headless 测试浏览器，不接管用户个人浏览器会话。
- `AC-S13`：资源清理维护入口具有真实 Worker 测试；文档明确它是人工命令还是定时调用。若本阶段不接入调度，不得声称存在自动后台回收。
- `AC-S14`：全量门禁零退出码；ESLint warning 应清零或在规划中列为明确延期，禁止新增文件级规则压制。

## 状态验收矩阵

| 场景 | D1 最终状态 | R2 最终状态 | API/UI 结果 | 证明层 |
|---|---|---|---|---|
| 同版本并发 PATCH | 仅一个 token 对应的完整聚合提交，token 清空 | 无误删 | 一个成功、一个 `VERSION_CONFLICT` | Worker 并发测试 |
| batch 中途失败 | 主表、关联表、asset 引用均保持原值 | 不变 | 安全错误，抽屉保留草稿 | Repository/Worker 故障注入 |
| 打开已有 QR 群组 | ready asset 与引用保持不变 | 对象存在 | 抽屉显示远端二维码 | Vue + Playwright |
| 上传 QR 后保存 | staged→ready，`ref_count` 正确 | 对象存在 | 保存成功，主页可查看 | Worker + Playwright |
| 上传 QR 后取消/删除整行 | staged asset 行删除 | 对象删除 | 抽屉关闭或草稿继续可用 | Vue + Worker |
| 删除最后一个 ready QR 引用 | `ref_count=0`，进入清理并最终删除或 `delete_failed` | 成功删除或保留待重试 | 保存成功；失败可维护重试 | Worker |
| purge ready asset | 数据和引用不变 | 对象存在 | `STATE_CONFLICT` | Worker |
| R2 删除失败后重试 | 先 `delete_failed`，重试成功后删除行 | 重试后不存在 | 首次依赖错误，维护命令可恢复 | Worker 故障注入 |
| 带 QR 永久删除 | 群组关联删除，无孤立 ready asset | 无引用对象删除 | `purgeState=done` 或安全可重试错误 | Worker |

## 收敛阶段不在范围

- 重新设计筛选、搜索、排序、抽屉布局或公开二维码视觉。
- 新增角色、审计历史、批量操作、FTS 或其他原父任务范围外能力。
- 为了规避原子性要求而放宽 `AC-13`。
- 继续用时间戳、版本号或事后补偿替代唯一 mutation token。

当前没有阻塞性的产品问题；剩余工作均为已确定的实现与验证任务。
