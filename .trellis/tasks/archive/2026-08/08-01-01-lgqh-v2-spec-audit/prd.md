## 1. 背景与用户价值

当前项目已经形成公开端、管理端、API、D1、R2、安全和自动化测试基础。本次 V2 会重构公开首页、群组卡片/详情、自定义板块、主题设计、管理分页、响应式表格、数据库结构和回归测试。

V2 不能直接依照产品 PRD 开始编码，因为仓库已有 Spec、归档任务、历史 Bug 修复、状态机、资源生命周期、分页和测试约束。审计的用户价值是把“产品想要什么”和“系统真实能做什么”之间的事实差异显式化，避免：

- 重做已经存在且经过验证的能力。
- 用错误字段名、状态名、路由名或模块名进入后续设计。
- 破坏认证、CSRF、版本冲突、回收站和 R2 清理。
- 让公开端泄露已下架、回收站或永久删除数据。
- 让迁移、分页、视觉回归和跨任务所有权在实现阶段才暴露冲突。

## 2. 目标

### 2.1 核心目标

在不修改业务代码和正式 migration 的前提下，完整理解当前实现、项目约束、历史决策和测试覆盖，并回答：

1. 当前系统的真实行为是什么。
2. 当前 Spec 规定了什么。
3. Spec、代码与测试是否一致。
4. V2 总 PRD 是否与当前架构、数据模型或领域规则冲突。
5. V2 PRD 是否包含错误的现状假设。
6. 哪些能力可直接复用，哪些模块必须修改。
7. 哪些需求需要补充约束、验收或测试。
8. 哪些冲突可通过技术设计解决，哪些需要产品决策。
9. 后续 T02–T10 实际影响哪些文件、模块、API、migration 和测试。

### 2.2 PRD 改进目标

只能依据证据提出以下改进：

- 修正错误的现状描述。
- 补充遗漏约束、迁移要求、兼容性要求、验收条件和测试要求。
- 更正字段名、状态名、路由名和模块名。
- 调整不合理的后续任务边界、依赖、文件所有权和风险等级。
- 标记仍需用户决策的 C4/C5 问题。

不得未经用户授权改变 V2 已冻结产品目标。已确认的“已下架完全不公开”必须作为公开数据边界执行。
