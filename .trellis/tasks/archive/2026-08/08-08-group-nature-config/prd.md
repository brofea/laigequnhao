# 群组性质候选词可配置

## 目标与价值

让部署者只需修改 `site.config.ts` 即可维护群组性质的前端候选项，而不必改动表单源码。群组性质将作为中文文本原样贯穿 API 与 D1；旧部署数据库升级时自动解除旧枚举约束，并将既有值转换为新的中文值。

## 已确认背景

- Issue #32 指出 `src/components/AdminEditForm.vue:101` 将“兴趣、工具、同城”硬编码为群组性质候选项；同一表单已从 `site.config.ts` 读取平台候选项（`src/components/AdminEditForm.vue:116`）。
- `SiteConfig` 的 Zod schema 目前没有性质候选项（`shared/domain/config.ts:77`）。
- 当前领域模型和 API 契约将性质限定为 `official | interest`（`shared/domain/group.ts:4`），初始 D1 schema 也用同一 `CHECK` 约束（`migrations/0001_initial.sql:10`）。
- 前端适配层当前把旧 API 值显示为“工具”或“兴趣”（`src/features/groups/adapters.ts:54`）。
- SQLite/D1 无法直接删除列级 `CHECK`；迁移必须重建 `groups` 表并复制全部数据。既有子表通过外键关联 `groups`，迁移须保证其关系、索引和所有现有列不丢失。

## 范围

1. 在 `site.config.ts` 增加群组性质候选列表，默认值为“官方、非官方、社区、活动、关系”。
2. 在共享站点配置 schema 中校验该列表：至少一个非空项、无重复项。
3. 将 `GroupKind`、公开/管理 DTO、投稿、管理创建和更新 API 契约从封闭枚举改为受长度与空值约束的文本，允许中文性质原样往返与保存。
4. 将前端展示模型的性质字段改为文本，并使管理端 `Select` 仅从站点配置的候选列表生成选项；不提供自由输入。
5. 新增有序 D1 migration：在全新数据库中由完整 migration 链建表；在已升级到 `0001`–`0004` 的旧表上重建 `groups` 以移除 `kind` 的旧枚举 `CHECK`，保留全部列、数据、索引和子表关联；将旧值 `official` 映射为“官方”、`interest` 映射为“兴趣”。
6. 补齐配置、契约、前端组件/适配及旧库升级的测试。
7. 保持 `pnpm deploy` 的部署顺序：先由 Wrangler 应用未记录的远程 D1 migrations，再发布 Worker；已记录且结构正确的数据库不得执行任何表重建。

## 明确不在范围内

- 不新增在线编辑站点配置的管理界面。
- 不将后端 API 限制为 `site.config.ts` 的候选列表；配置是浏览器 UI 的选择来源，API 保持可持久化的文本字段，便于历史数据和受信任管理工具兼容。
- 不改变群组状态、平台、标签、加群方式、资源或板块业务规则。
- 不主动修改部署外的生产数据；提交的 migration 由现有部署流程在目标 D1 上执行。

## 关键决定

| 决定 | 结论 |
| --- | --- |
| 存储语义 | `kind` 与平台一样为文本字段，中文值原样保存；前端不允许自由输入。 |
| 默认候选项 | 官方、非官方、社区、活动、关系。 |
| 旧值映射 | `official → 官方`；`interest → 兴趣`。 |
| 旧库升级 | 新增 migration 重建受约束的 `groups` 表，不修改已应用 migration；复制所有列和关联数据。 |
| 幂等部署 | 以 D1 的 `d1_migrations` 记录为事实来源：全新库建表、旧版本库升级、已迁移库跳过，不在每次部署检查或重建表。 |

## 验收标准

- [ ] 修改 `site.config.ts` 的候选列表后，管理端“群组性质”选择控件随之变化，且没有可输入的自由文本控件。
- [ ] 默认配置恰含“官方、非官方、社区、活动、关系”五项。
- [ ] 空、重复或没有候选项的配置在启动解析时被拒绝。
- [ ] 共享契约可接受、返回和保存合规的中文性质；不再拒绝非 `official | interest` 的文本性质。
- [ ] API 到前端展示的数据流不再把性质改写为“工具”或其他旧映射，保存后显示的性质与存储值一致。
- [ ] 从 `0001`–`0004` 数据库升级后，旧 `official` 记录为“官方”、旧 `interest` 记录为“兴趣”；群组所有列、标签、加群方式和板块关联仍然完整。
- [ ] 升级后的 D1 接受新的中文性质值，不再受旧 `CHECK` 枚举限制。
- [ ] 全新数据库通过完整 migration 链得到正确 schema；从 `0001`–`0004` 升级时才重建并迁移数据；再次执行部署 migration 时，`groups` 表和数据不发生变化。
- [ ] `pnpm deploy` 在 Worker 发布前应用未完成的远程 D1 migrations；migration 失败时 Worker 不发布。
- [ ] 相关单元、组件、Worker migration/路由测试以及项目质量门禁通过。

## 风险与缓解

- 重建父表时外键或索引遗漏会损坏关系或查询性能：migration 显式列出全部现有列，使用临时表交换，并以升级测试验证子表、板块关联、旧值映射及任意新值插入。
- 配置候选项随后被删除时，旧群组仍可带有不在当前候选项中的性质：展示保持原值，编辑界面仍由配置候选项决定；本任务不自动重分类历史记录。
- D1 的有序 migration 以 `d1_migrations` 记录判断是否已应用。若有人在记录已完成后手工破坏生产表结构，自动重跑旧 migration 会掩盖异常且有数据风险；该类数据库损坏应通过新的受审查修复 migration 处理，而非在每次部署中重建表。
