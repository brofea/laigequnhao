# 修复图片上传相关 BUG（seed、展示与完整上传链路）

## Goal

打通头像和二维码从浏览器选择图片、客户端压缩为 WebP、上传、R2/D1 资源登记、群组聚合保存到公开展示的完整链路。管理员和公开投稿都能可靠上传 PNG/JPG/WebP 图片；图片生命周期继续可删除、替换和清理。

## 已确认的现状与根因

1. `POST /api/v1/admin/assets` 已存在，但要求上传内容本身就是最终 WebP；当前 `AdminEditForm.vue` 在管理模式直接把用户选择的原始文件提交，因此 PNG/JPG 会被 `UNSUPPORTED_MEDIA_TYPE` 拒绝。
2. 公开投稿模式只用 `FileReader` 做本地预览，不上传资源；`POST /api/v1/submissions` 当前是纯 JSON，`submissionRequestSchema` 没有资源字段，`submission-service.ts` 也不会 adopt 图片资源。
3. 管理端群组创建/更新与 `group-repository.ts` 已具备 staged asset、adoption、`ref_count` 和 R2 清理逻辑；这部分应复用并补齐公开投稿路径。
4. `shared/contracts/asset.ts` 已有 Logo 80 KB、二维码 400 KB、最长边和质量递减常量；`scripts/seed-local.mjs` 已有基于 `sharp` 的压缩语义，可作为浏览器压缩行为的参考。
5. 后端当前已校验 WebP 签名、实际字节数和尺寸，但尺寸上限仍是通用 4096；最终校验应与用途专属压缩配置一致。

## Requirements

### R1. 浏览器图片处理

- 支持选择 PNG、JPG/JPEG、WebP；在浏览器完成解码、等比缩放和 WebP 编码后再上传。
- 压缩参数集中配置，至少包括 Logo/二维码各自的最长边、起始质量、最低质量、质量递减步长和目标字节上限。
- Logo 保留透明度；带 alpha 的 PNG 经过压缩后仍使用带透明度的 WebP。
- 二维码统一铺白底并输出不透明 WebP。
- 客户端在原始文件过大、浏览器不支持图片解码/Canvas/WebP、压缩后仍超过硬上限时给出可见错误，不上传不合格文件。
- 原图 5 MB 是浏览器选择阶段的限制；后端不得把它当成可验证的原图限制，而要独立限制 multipart 请求总字节数和最终压缩文件实际字节数。
- 预览对象 URL 或其他临时资源在替换、关闭和卸载时清理，不泄漏 Blob。

### R2. 管理端上传与保存

- 管理员上传头像和二维码时，表单只把浏览器压缩后的 WebP 发送到资源接口。
- 上传成功后立即使用后端返回的 `publicUrl` 预览，并把稳定的 `r2Key`/asset ID 保存在草稿。
- 管理员创建、替换、移除头像及二维码时，群组保存必须继续通过现有聚合事务完成 adoption、引用计数和孤儿资源清理。
- 保存后重新读取管理 DTO 与公开 DTO，图片 URL、尺寸、用途和资源状态均正确。

### R3. 公开投稿上传与保存

- 当前公开投稿只携带单张可选图片；用户选择原图后，图片只在浏览器本地压缩和预览，不提前请求上传接口。
- 点击最终提交时，压缩后的 WebP 与投稿表单、Turnstile token 通过同一个 `multipart/form-data` 请求发送，由后端统一校验并写入 R2/D1/群组聚合。
- 公开投稿单张图片按头像用途保存；二维码继续由管理端的二维码字段独立维护，不在本次公开投稿请求中引入第二张图片。
- 投稿失败或后端写入失败时，不得创建半成品群组；后端对已经写入 R2 但 D1 失败的对象执行同步补偿删除，并返回安全错误。
- 最终投稿仍必须通过 Turnstile 和现有限流。

### R4. 后端校验与限制

- Logo 最终 WebP 最大 80 KB，二维码最终 WebP 最大 400 KB；限制由后端以实际字节数强制执行。
- 后端只接受有效 WebP 作为最终资源，验证 RIFF/WEBP 签名、实际宽高、用途、用途专属最长边和字节上限；不得信任客户端声明的元数据。
- R2 对象使用 `image/webp` 元数据，D1 asset 记录保存最终宽高、字节数、用途和生命周期状态。
- 管理上传与公开投稿共享图片校验和底层资源写入能力，避免两套不一致的图片安全规则；管理端继续返回 staged DTO，公开投稿直接写入 ready 资源。
- 公开投稿图片不新增临时上传接口、staged/adopt 流程或公开图片专用限流；图片上传与最终投稿共用一次 Turnstile 校验和一次请求。
- 后端必须对实际 multipart 文件再次执行源文件大小、WebP 签名、完整解码、用途、宽高和总像素限制校验；不能信任前端声明的 MIME、宽高或字节数。
- 后端校验顺序固定为：请求体总大小与文件实际字节数 → WebP 结构、真实宽高读取 → 宽高/总像素限制 → 完整解码；宽高和像素限制通过后才允许进入解码阶段。

### R5. 既有功能兼容

- 不改变 seed 的图片规划、压缩语义、群组规划或现有资源删除/恢复/永久清理状态机。
- 不破坏当前已能工作的管理员删除头像/二维码、共享资源引用计数、失败重试和公开图片读取。
- 旧的无资源群组、旧的 ready 资源和当前公开 API 字段保持兼容。

## Acceptance Criteria

- [ ] 浏览器单测覆盖 JPG、透明 PNG、WebP、最长边缩放、质量递减、目标字节边界、二维码铺白、压缩失败和对象 URL 清理。
- [ ] 管理端通过真实表单选择 PNG/JPG 后，网络请求体是 WebP；头像和二维码上传成功后可预览，创建/更新后重新读取仍可展示。
- [ ] 公开投稿通过真实表单携带单张压缩头像提交后，pending 群组、assets、Logo 引用计数和 R2 对象一致。
- [ ] 后端拒绝非 WebP、签名错误、用途不匹配、超出 80 KB/400 KB 和用途专属尺寸的请求；管理端合格上传返回 staged asset DTO，公开投稿合格文件随群组事务生成 ready asset。
- [ ] 后端分别覆盖 multipart 总大小、压缩文件字节数、宽高和总像素边界；不以原图 5 MB 冒充后端校验。
- [ ] 合法二维码经过压缩后具备可执行的真实扫码验收，不只验证 MIME、签名或解码成功。
- [ ] 资源替换、移除、投稿失败和 D1/R2 补偿删除不留下错误引用或不可回收 R2 对象。
- [ ] D1/投稿失败后的 R2 补偿删除失败会记录 request ID、R2 key 和可重试清理状态，并有后续清理路径。
- [ ] 现有 seed 幂等 SQL 测试、管理员资源生命周期测试、群组聚合测试、公开投稿测试继续通过，并新增跨层上传回归测试。
- [ ] `pnpm lint`、`pnpm format:check`、`pnpm typecheck`、`pnpm test`、`pnpm test:workers`、`pnpm test:e2e`、`pnpm build` 通过；已知并行基线失败必须单独记录。

## Out of Scope

- 不增加服务器端 PNG/JPG 转码；服务器只负责最终 WebP 的安全校验、存储和聚合采用，转码责任在浏览器。
- 不新增图片裁剪器、滤镜、画廊、多图头像或用户账号体系。
- 不把压缩参数做成管理员运行时 UI；本任务要求集中代码配置并由前后端共享/对齐。
- Cloudflare 远程部署验证不属于本次验收；必须通过本地 workerd 与 Workers Vitest，不能只依据依赖文档宣称兼容。

## 已确认的产品决策

- 不新增公开 staged 图片上传接口。
- 公开投稿只支持单张可选图片；原图最大 5 MB，前端压缩后的 WebP 与表单在最终提交时一次发送。
- 公开投稿由同一个后端请求统一执行 Turnstile、图片校验、R2 写入和 D1 群组写入；失败时做 R2 补偿删除。
- 管理端仍可按现有认证资源接口分别上传头像和二维码，但必须先经过同一套浏览器压缩器。
