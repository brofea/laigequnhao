# 网站 V2 大版本升级总任务技术设计

## 1. 设计范围与原则

本文件将 `docs/PRD/v2/RPD.md` 中的产品要求转换为跨层技术边界、数据流、兼容策略和集成约束。它只描述总任务的架构与决策，不替代后续子任务的局部设计。

总体原则：

1. 保留现有认证、提交、点赞、图片上传、R2 生命周期、回收站、版本冲突和 cursor pagination 能力。
2. 共享 Contract 先于跨层实现，前端不直接依赖 Functions 内部类型，后端不重复维护前端校验规则。
3. 产品状态和数据库状态保持可追踪；展示排序可以计算，但不应通过定时任务覆盖人工位置。
4. 公共端按区域隔离加载失败，管理端写操作沿用现有安全和原子批量模式。
5. 迁移以可回滚的增量变更为主，先兼容旧代码，再启用新路径，避免一次性删除旧能力。

## 2. 总体边界

```text
共享 Contract / Domain
  ├─ ThemePreference、BoardSortMode、宽度校验、公开/管理 DTO
  ├─ 前端 API 解析与表单校验
  └─ Functions API 输入输出校验

公开端 Vue
  ├─ HomeView：默认首页/搜索状态/区域容器
  ├─ GroupCard、GroupDialog、Carousel：通用交互展示
  ├─ Theme/Header：全站 Token、主题、顶栏
  └─ composables：URL 状态、请求生命周期、无限滚动、焦点管理

管理端 Vue
  ├─ 群组页：固定 50 条页码分页与响应式表格
  ├─ 板块页：板块容器与成员表格
  └─ 现有抽屉/认证/脏表单/冲突处理能力

Pages Functions / Hono
  ├─ 公开查询：发现、标签、板块、目录、详情
  ├─ 管理 API：板块 CRUD、排序、成员、页码列表
  ├─ 现有群组/提交/点赞/资源路由
  └─ 认证、CSRF、版本冲突、限流和错误处理

D1 / R2
  ├─ groups.last_published_at
  ├─ boards、board_groups、索引、外键
  └─ 既有图片资源与回收站清理机制
```

总任务负责这些边界之间的集成一致性；每个功能子任务只能在其明确所有权范围内修改代码。

## 3. 共享 Contract 与领域规则

### 3.1 主题

`ThemePreference` 是用户偏好，不等同于最终渲染主题。建议在共享层区分：

- 偏好：`system | light | dark`，负责持久化和用户控件。
- 实际主题：`light | dark`，由偏好和 `matchMedia('(prefers-color-scheme: dark)')` 推导。

自动模式需要覆盖 iOS、macOS、Windows、Android 等支持 `prefers-color-scheme` 的常见系统，并在系统主题变化时实时跟随，而不是只在首次加载时读取一次。

非法持久化值必须在解析边界回退到 `system`。系统主题监听器在偏好为 `system` 时生效，其他偏好下不应覆盖用户选择。首屏脚本和 Vue composable 必须使用同一套合法值规则，避免首屏和挂载后状态不一致。

### 3.2 显示宽度

显示宽度函数应放在前后端均可依赖的共享 domain 层，输入为已规范化的字符串，输出为整数宽度。Unicode 分段和 Emoji 字素簇处理应有独立单元测试；如果运行环境无法使用同一 Unicode 库，应固定算法和测试样例，禁止前后端各自用近似的 `length` 或正则实现。

标题/简介 Schema 在共享层定义上限，服务端在 API 边界再次解析，前端表单只负责即时反馈，不替代服务端校验。

### 3.3 板块

建议共享以下核心结构（实际字段以现有 domain 命名审计结果为准）：

- `Board`：`id`、`title`、`is_enabled`、`position`、`sort_mode`、`version`、时间字段。
- `BoardMember`：`board_id`、`group_id`、`position`、时间字段，并附带公开/管理所需群组摘要。
- `BoardWithGroups`：板块信息、成员总数、可见成员和局部状态。
- 管理端页码结果：`items`、`page`、`pageSize`、`totalItems`、`totalPages`。

状态过滤必须集中在 repository/service 边界：公开查询只接收已发布内容；管理添加器允许已发布和已下架但排除回收站；回收站和永久删除流程负责清理关联。

## 4. 数据模型与迁移设计

### 4.1 增量 Schema

在现有 `groups` 上新增可空 `last_published_at`，类型与现有时间字段一致，并为“已发布 + 时间倒序 + 稳定 ID”查询建立合适索引。

新增：

```text
boards
  id, title, is_enabled, position, sort_mode, version,
  created_at, updated_at

board_groups
  board_id, group_id, position, created_at
  PRIMARY KEY (board_id, group_id)
```

必须有板块位置查询索引、板块成员 `board_id + position` 查询索引、外键和删除级联/显式清理策略。D1 外键行为必须与现有配置和 migration 顺序一致。

源 PRD 要求的字段契约如下，后续审计若发现项目命名不同，只能做有证据的字段映射，不能遗漏语义：

```text
groups.last_published_at       nullable，与现有时间字段类型一致

boards
  id
  title
  is_enabled
  position       板块在首页中的顺序
  sort_mode      manual_asc | manual_desc | hourly_random
  version        并发修改保护
  created_at
  updated_at

board_groups
  board_id
  group_id
  position
  created_at
  PRIMARY KEY (board_id, group_id)
```

除主键外，还需满足：板块删除时级联/显式清理成员关联；群组永久删除时清除成员关联；存在 `board_id + position` 查询索引和板块位置查询索引；外键行为与当前 D1 配置兼容；成员上移、下移和板块拖拽不得留下重复位置、丢失位置或部分更新。

完整的源 PRD 表结构草案为：

```text
boards
- id
- title
- is_enabled
- position
- sort_mode
- version
- created_at
- updated_at

board_groups
- board_id
- group_id
- position
- created_at
```

### 4.2 发布时间状态机

发布时间更新是领域状态转换，不应散落在多个路由：

```text
旧状态 != published && 新状态 == published
  → 写入新的 last_published_at

旧状态 == published && 新状态 == published
  → 保留原 last_published_at

published → delisted / recycle bin
  → 保留历史值，但公开查询过滤
```

从回收站恢复到可编辑状态不自动恢复板块关联；再次发布时按“非已发布 → 已发布”处理。

状态转换契约为：

```text
旧状态 != published && 新状态 == published
  → 写入新的 last_published_at

旧状态 == published && 新状态 == published
  → 保留原 last_published_at

published → delisted / recycle bin
  → 保留历史值，但公开查询过滤
```

状态转换入口至少覆盖以下等价场景：

```text
非已发布状态 → 已发布状态
```

### 4.3 迁移与默认数据

迁移顺序建议为：新增列和表/索引 → 回填可靠时间 → 幂等创建默认板块 → 更新共享 Contract 和服务 → 开启新读写路径。

回填规则优先采用真实可识别发布时间，缺失时使用 `created_at`，从未发布保持 NULL。默认板块必须以稳定条件或唯一约束保证幂等；已有板块数据不能被覆盖。

发布前必须在本地 D1 和 Workers 测试数据库分别演练：重复迁移、旧数据回填、旧代码读取新增结构、新代码在迁移未完成时的错误行为和回滚后的读路径。

## 5. API 与数据流设计

### 5.1 公开首页读取

推荐使用多个逻辑独立的公开查询接口，而不是一个强耦合的首页聚合接口：

1. 发现新群：最多 10 条，按 `last_published_at DESC, id DESC`。
2. 标签聚合：一次查询返回已发布标签及计数。
3. 启用板块：返回板块顺序、排序模式和已发布成员摘要。
4. 所有群组/搜索：沿用现有 cursor pagination、搜索语义和旋转排序。
5. 群组详情：只允许读取已发布群组及其公开加群方式。

独立接口的理由是：板块或标签失败时可以在页面局部显示错误，目录和搜索仍可用；它也能保留现有目录 cursor 接口，减少 V2 首页重构对既有分页的耦合。可以在客户端并行请求，但每个区域拥有自己的 loading、empty、error 和 retry 状态。

具体 URL、响应信封和分页字段必须先对照当前 API 规范和源码确认，再写入各子任务设计；不得仅根据源 PRD 假定路径已经存在。

### 5.2 管理 API

管理端 API 按领域分组：

- 板块列表/创建/编辑/启停/删除。
- 板块整体位置批量更新。
- 成员添加/移除/上移/下移和排序模式更新。
- 管理群组页码列表与总数。

所有写操作统一经过认证、CSRF、Zod、版本冲突和原子批量边界。位置更新需要在一次 D1 batch/事务语义内完成，失败时返回稳定错误类别，前端回滚乐观状态。

管理端页码查询固定 `pageSize = 50`，服务端计算 `totalItems` 和 `totalPages`，排序条件必须补稳定次排序字段。页码、筛选、搜索和排序状态由前端 URL 解析器统一读写，所有改变查询条件的动作重置到第一页。

管理 API 的能力清单必须逐项覆盖：板块列表、创建、编辑、启用/关闭、删除、调整板块顺序、添加板块成员、移除板块成员、成员上移/下移、修改排序模式和管理端群组页码列表。管理端筛选能力必须继续覆盖多状态筛选和回收站。

公开 API 的能力清单必须逐项覆盖：发现新群、所有标签统计、启用板块和已发布成员、所有群组 cursor pagination、搜索结果 cursor pagination、已发布群组详情。公开接口不得返回下架、回收站或永久删除群组的敏感内容。

### 5.3 URL 与交互状态

公开端使用 `q` 和 `group` 两个互不覆盖的 URL 状态：

- 打开详情只新增/替换 `group`，保留 `q`。
- 关闭详情只移除 `group`。
- 浏览器返回/前进由 URL 驱动弹窗开关和焦点恢复。
- 无效 `group` 深链接只返回非敏感错误，并允许清理参数。

管理端使用页码、搜索、状态、回收站、排序字段和方向的集中 query state；不要让多个组件分别拼接 query，避免浏览器历史和筛选回页规则分叉。

## 6. 排序与分页

### 6.1 公开目录

完整目录继续沿用当前时区感知旋转规则，V2 不重新发明排序算法。审计阶段必须核对旋转 epoch、站点时区、槽位、稳定字段、搜索耦合和 cursor 组成；新建“发现新群”查询不得误改目录算法或删除现有时间固定测试。

公开列表仍以服务端返回顺序为准，前端只负责追加、去重、加载更多和请求竞态处理。

### 6.2 板块顺序

- `manual_asc`：按持久化位置升序。
- `manual_desc`：按持久化位置降序，管理端仍以标准位置编辑。
- `hourly_random`：以板块、站点时区的小时槽位和群组 ID 生成稳定 key；同小时稳定、跨小时变化、不写库。

共享类型契约为：

```ts
type BoardSortMode =
  | 'manual_asc'
  | 'manual_desc'
  | 'hourly_random'
```

### 6.3 管理分页

管理端从 keyset/cursor 列表切换为页码列表只影响管理查询；不得把页码逻辑泄漏到公开目录。稳定排序是页码正确性的前提，尤其要覆盖第 50/51 条、相同排序值和跨页更新场景。

## 7. 前端组件与状态边界

### 7.1 设计 Token 与主题

基础 Token 以 CSS 自定义属性为单一视觉运行时来源，Tailwind 只做映射，不在页面组件散落任意色值、间距、圆角和阴影。浅色和深色同时定义背景、层级、文字、边框、阴影、交互态和状态色。

Theme composable 负责偏好、实际主题、持久化和系统监听；首屏脚本负责尽早设置根节点主题标记。顶栏和公共状态组件只消费 Token，不重新解释主题。

### 7.2 卡片、弹窗与 Carousel

GroupCard 只发出“打开详情”和“切换点赞”等语义事件；点赞按钮阻止事件冒泡，卡片主体不包裹嵌套按钮。GroupDialog 负责 URL、焦点陷阱、滚动锁定、加群方式和分享反馈，不把详情逻辑复制到卡片。

Carousel 抽象拖动阈值、点击抑制、横向滚轮条件、边界恢复纵向滚动和键盘操作；公开板块和“发现新群”只传入内容，不各自实现一套滚动逻辑。

### 7.3 首页区域

HomeView 负责区域编排和搜索模式切换；各 composable 负责独立请求生命周期。建议将“发现、标签、板块、目录/搜索”视为可观测的区域状态，不使用一个全局 loading/error 覆盖全部页面。

目录 composable 延续当前 AbortController、URL 搜索词、cursor、去重和 IntersectionObserver 机制；搜索重置只影响目录状态，不清除 `group` 详情状态，除非用户明确关闭。

默认首页的区域数据流为：HomeView 编排顶栏和搜索框；默认模式并行加载发现、标签、启用板块和目录；搜索模式只加载搜索目录；每个区域独立维护初始、等待、加载、继续加载、空、失败和重试状态。无数据时分别展示：发现空状态、标签空状态、启用空板块状态、所有群组空状态和搜索无结果/提交引导。单个板块失败不得使整个首页白屏。

### 7.4 管理端

群组页负责 URL query、页码和表格列优先级；现有编辑抽屉、脏表单守卫、冲突处理和图片上传能力保持复用。板块页负责容器顺序和成员操作，成员“移除”只删除关联，不调用群组删除。

## 8. 错误、并发与安全

- 公开区域：单个发现/标签/板块请求失败只影响该区域，目录失败仍提供重试和非白屏反馈。
- 管理写入：以版本号/突变令牌作为并发保护；batch 失败时前端恢复提交前状态并展示可理解错误。
- 回收站：状态变更与板块关联清除必须在同一原子边界；永久删除保证关联清理后才完成。
- API：复用现有认证、CSRF、Zod、错误封装、日志脱敏和权限检查。
- 公开过滤：repository 查询层就过滤非公开状态，避免在 UI 层拿到敏感数据后再隐藏。
- 资源：不改变 R2 key、WebP 处理、删除和清理生命周期。

安全契约具体包括管理员认证、CSRF 保护、Zod 校验、版本冲突保护以及现有突变令牌或原子批量模式。回收站状态变化和板块关联删除必须处于同一原子边界；从回收站恢复后不自动恢复旧关联，并向管理员明确提示。

## 9. 非功能设计约束

- 所有群组和搜索结果保持 cursor pagination；管理端固定每页 50 条；发现新群最多 10 条。
- 标签数量使用单次聚合查询；板块成员接口避免明显 N+1 查询。
- 图片继续懒加载并保持固定比例，防止布局跳动。
- 板块成员管理表固定高度、内部滚动，避免长列表撑大页面；公开 Carousel 不设产品硬上限，但实现需避免明显主线程阻塞。
- 首屏主题设置必须在 Vue 挂载前完成。
- 每小时随机必须可计算、可缓存、可测试，不运行每小时写数据库的定时任务。
- 所有操作可键盘完成；焦点明显；弹窗焦点锁定和恢复；Carousel 支持左右键；图标按钮有可访问名称；颜色不作为唯一状态；浅色/深色有合理对比度；触摸目标尺寸合理；支持 `prefers-reduced-motion`；Toast/错误可被辅助技术感知；表格保留正确表头和单元格语义。

## 10. 发布、兼容与回滚

### 10.1 推荐发布顺序

1. 完成 Spec/代码审计并修订受影响的规划边界。
2. 用户确认设计语言和视觉样例。
3. 合并共享 Contract、时间字段、板块表和索引的增量迁移。
4. 上线后端读写与安全控制，并通过 Workers 测试。
5. 上线主题/Token/顶栏和通用展示组件。
6. 上线首页区域、搜索、详情和 Carousel。
7. 上线管理端板块页面、群组分页和响应式表格。
8. 执行完整回归、视觉、无障碍、迁移演练和发布验收。

### 10.2 兼容策略

- 新字段和新表先以 additive migration 方式加入，旧代码只需忽略新增结构即可继续读取原群组字段。
- 新代码在依赖新表/字段时对迁移未完成返回稳定、可观测错误，不泄露内部 SQL 细节。
- 旧 API 和既有路径在新前端切换前保持可用，除非子任务设计明确写出兼容窗口和迁移时序。
- 不在 V2 首次发布中删除旧列、旧资源或旧认证路径。

### 10.3 回滚点

- 共享 Contract 变更后：若前后端解析不一致，先回退客户端入口，保留 additive schema。
- 后端板块 API 后：若关联/并发测试失败，关闭新入口并保留表数据，不清理既有群组。
- 首页/管理端切换后：若出现公开泄露或核心回归，恢复旧页面入口，保留新表和字段供后续修复。
- 迁移失败：停止新代码发布，修复 migration 或恢复到兼容的旧读路径；禁止通过删除迁移结果来“回滚”。

| 视觉模板尚未提供 | 在视觉子任务开始前补齐并经用户确认；未确认前不冻结 Token |
| 源 PRD 使用 `RPD.md` | 作为现有事实记录，不重命名源文件 |

| 标签稳定次排序 | 当前采用“数量降序 + 标签名稳定次序”的产品要求，字段/大小写规则由审计阶段确认 |
| 现有旋转排序与发现新群 | 分离为两个查询能力；审计必须保护现有旋转和 cursor 测试 |
| 默认板块创建时机 | 迁移/初始化均需幂等，最终以现有 migration 生命周期选择唯一入口 |
| 大板块 DOM 规模 | 成员表固定高度内部滚动；公开 Carousel 避免无界同步渲染，并用性能测试验证 |
| 公开数据泄露 | 查询层按状态过滤，详情、板块和目录分别测试已下架/回收站/删除场景 |
