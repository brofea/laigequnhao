# 1. 背景

V2 升级需要新增以下数据能力：

1. 记录群组最后一次进入已发布状态的时间
2. 支持管理员创建和维护多个自定义板块
3. 支持一个群组同时属于多个板块
4. 支持板块内群组人工排序和每小时稳定随机
5. 为群组标题和简介建立统一显示宽度限制
6. 让前端和后端使用完全一致的校验规则

这些能力会被后续任务依赖：

* 子任务 05：板块后端服务与 API
* 子任务 06：群组卡片与详情弹窗
* 子任务 07：首页信息架构与搜索
* 子任务 08：管理端板块管理
* 子任务 09：管理端群组分页与响应式表格
* 子任务 10：系统回归与发布验收

因此，本任务必须先建立稳定的数据表、字段、索引、共享类型和领域规则。

本任务不是板块功能的完整实现，而是板块功能和“发现新群”功能的数据基础。

# 2. 任务目标

## 2.1 发布状态数据基础

在群组数据中新增：

```text
last_published_at
```

用于记录群组最后一次从非已发布状态进入已发布状态的时间。

该字段将作为“发现新群”的主要排序依据。

## 2.2 板块数据基础

新增：

```text
boards
board_groups
```

支持：

* 多个板块
* 板块启用与关闭
* 板块之间排序
* 板块内部排序模式
* 一个群组加入多个板块
* 同一群组不能重复加入同一板块
* 已下架群组保留板块关联
* 后续在回收站流程中原子移除关联

## 2.3 字符显示宽度基础

建立前后端共享的显示宽度算法，实现：

* ASCII 和普通半角字符按 1 个单位计算
* 中文、日韩宽字符和全角字符按 2 个单位计算
* Emoji 字素簇按 2 个单位计算
* 组合字符不会被错误重复计数
* 浏览器、Node 测试和 Cloudflare Workers 结果一致

## 2.4 内容长度限制

冻结并实现：

```text
群组标题：最大 50 个显示宽度单位
群组简介：最大 1000 个显示宽度单位
```

前端和后端必须使用同一个共享实现。

## 2.5 安全迁移

迁移必须同时支持：

* 从现有生产数据库升级
* 从空数据库完整初始化
* 本地开发数据库
* Workers 测试数据库
* 后续 migration 继续演进

不得静默截断、覆盖或删除现有群组内容。

# 6. `last_published_at`

## 6.1 字段语义

`last_published_at` 表示：

> 群组最后一次从任何非已发布状态转换为已发布状态的时间。

它不是：

* 群组创建时间
* 群组最后编辑时间
* 群组审核时间
* 管理员最后保存时间
* 图片最后更新时间
* 点赞最后更新时间

## 6.2 字段所有权

该字段是服务端拥有的只读字段。

客户端不得直接：

* 创建该时间
* 修改该时间
* 覆盖该时间
* 通过 API 请求传入该时间

所有时间均由后端可信时钟生成。

## 6.3 存储格式

字段类型、精度和时区格式必须遵循现有群组时间字段约定。

无论当前项目使用：

* Unix 秒
* Unix 毫秒
* ISO 8601 字符串
* SQLite 时间字符串

`last_published_at` 都必须与现有时间字段保持一致。

时间应表达绝对时刻，原则上以 UTC 存储。

站点时区只影响展示或时间槽位计算，不改变发布时间的存储含义。

## 6.4 可空规则

以下群组的 `last_published_at` 可以为空：

* 从未发布过的草稿
* 从未发布过的待审核群组
* 从未发布过的已下架记录
* 其他从未进入已发布状态的记录

只要群组至少成功进入过一次已发布状态，该字段就不应再因为普通下架而清空。

# 7. 发布时间更新规则

## 7.1 核心判断

发布时间只在以下转换发生时更新：

```text
旧状态 != 已发布
且
新状态 == 已发布
```

必须使用代码中的真实状态枚举，而不是直接依赖中文状态文字。

## 7.2 必须更新时间的场景

至少包括：

* 新建群组并直接保存为已发布
* 草稿变为已发布
* 待审核变为已发布
* 已下架群组重新发布
* 从回收站恢复并直接进入已发布状态
* 其他合法非发布状态进入已发布状态

## 7.3 不得更新时间的场景

至少包括：

* 已发布群组修改标题
* 已发布群组修改简介
* 已发布群组修改平台
* 已发布群组修改标签
* 已发布群组修改头像
* 已发布群组修改加群方式
* 已发布群组修改点赞相关数据
* 已发布状态保存后仍保持已发布
* 已发布群组发生版本冲突且更新失败
* 非已发布状态之间互相转换
* 已发布群组变为已下架
* 已发布群组进入回收站

## 7.4 时间一致性

一次群组状态写操作中：

* 状态更新
* `last_published_at` 更新
* 版本号更新
* 其他同批字段更新

必须处于同一逻辑事务或同一个原子数据库操作中。

不得出现：

* 状态已经变为已发布，但发布时间仍为空
* 状态更新失败，但发布时间被更新
* 版本冲突后发布时间被错误刷新
* 重试请求每次都更新发布时间

## 7.5 重试与幂等

如果项目已有突变令牌、版本号或幂等机制，本任务必须保持兼容。

对于同一次逻辑发布操作的重复请求：

* 已成功进入已发布状态后再次提交相同状态，不应刷新发布时间
* 失败重试只有在真实状态转换成功时才更新时间
* 版本冲突请求不得更新时间

# 8. 发布逻辑集中化

## 8.1 单一规则来源

应建立一个可测试的纯函数或领域方法，用于判断是否刷新发布时间。

示意语义：

```ts
shouldUpdateLastPublishedAt(previousStatus, nextStatus): boolean
```

具体名称遵守现有项目命名规范。

不得在多个 route 或组件中重复编写：

```ts
if (status === 'published') {
  // 更新时间
}
```

因为这种写法会导致已发布状态的普通编辑错误刷新发布时间。

## 8.2 覆盖所有写入入口

Agent 必须根据子任务 01 审计结果，检查所有可能修改群组状态的入口，包括：

* 管理端新建
* 管理端编辑
* 审核操作
* 下架
* 重新发布
* 回收站恢复
* 批量状态操作，如现有系统支持
* 测试或内部维护入口

不得只修改最常用的单个 route。

## 8.3 可注入时钟

为保证测试稳定，发布时间逻辑应使用项目现有的时间适配器或可注入时钟。

如果当前代码直接调用系统时间，应在不引入过度架构的前提下，使测试能够固定时间。

不得在测试中依赖真实当前时间并使用宽松误差断言替代确定性验证。

# 9. “发现新群”数据查询准备

本任务不实现公开“发现新群”接口，但数据库结构必须支持后续查询：

```text
只查询已发布群组
按 last_published_at 倒序
使用稳定次排序
最多返回 10 个
```

预期逻辑：

```sql
WHERE status = <published>
ORDER BY last_published_at DESC, id DESC
LIMIT 10
```

实际 SQL 使用当前项目真实字段名和 ID 类型。

## 9.1 稳定次排序

当多个群组拥有相同 `last_published_at` 时，必须使用稳定且唯一的次排序字段。

默认使用群组主键。

## 9.2 空值

已发布群组在迁移完成后原则上不应存在空的 `last_published_at`。

查询仍应对异常空值有确定行为，不能让排序完全不可预测。

迁移和后续状态逻辑应确保正常数据不会产生该异常。

# 10. 旧数据回填

## 10.1 已发布群组

现有已发布群组需要回填 `last_published_at`。

回填优先级：

1. 使用项目中现有且可信的首次或最近发布时间字段
2. 使用能够从历史状态记录可靠推导出的发布时间
3. 如不存在可信数据，使用群组 `created_at`

不得统一使用迁移执行时间。

否则部署后所有旧群组都会同时被视为刚刚发布。

## 10.2 非已发布群组

从未发布过的非已发布群组保持为空。

如果现有数据无法判断某个下架群组是否曾经发布过，不得凭空生成“最后发布时间”。

需要根据子任务 01 的数据事实和现有字段制定明确回填策略。

## 10.3 数据异常

迁移测试必须考虑：

* 已发布但 `created_at` 异常
* 时间字段为空
* 时间字段格式不一致
* 同一时间戳的大量记录

不得因为单条异常数据让整个迁移静默产生错误结果。

如生产数据存在需要人工处理的异常，应在实施文档中列出。

# 11. `boards` 表

## 11.1 表职责

`boards` 存储管理员可配置的首页板块。

每一条记录代表一个板块。

## 11.2 逻辑字段

至少包含：

```text
id
title
is_enabled
position
sort_mode
version
created_at
updated_at
```

实际数据库字段类型和默认值必须遵守现有项目约定。

## 11.3 字段含义

### `id`

板块唯一标识。

ID 类型应遵循当前项目的领域 ID 规范，不得无依据混用整数、随机 UUID 和文本 ID。

### `title`

公开首页显示的板块标题。

本任务不擅自冻结尚未由总 PRD定义的板块标题产品长度，但必须：

* 不允许空标题
* 在后续共享 Contract 中保留可扩展校验位置
* 避免数据库层使用过小固定长度造成未来迁移

### `is_enabled`

控制板块是否在公开首页显示。

未启用板块仍然：

* 保留记录
* 保留成员
* 允许管理员编辑
* 允许调整排序

### `position`

控制板块之间的管理顺序和公开展示顺序。

建议使用从 0 开始的非负整数，除非现有项目已有统一位置规范。

### `sort_mode`

板块内部公开展示排序模式。

允许值：

```ts
'manual_asc'
'manual_desc'
'hourly_random'
```

### `version`

用于后续管理端并发修改和版本冲突保护。

其语义应与现有群组版本字段保持一致。

### `created_at`

板块创建时间。

### `updated_at`

板块最后一次配置变更时间。

# 12. `boards` 约束

数据库层至少应保证：

* 主键唯一
* 标题不可为空
* `is_enabled` 只接受合法布尔表达
* `position` 不得为负数
* `sort_mode` 只能为允许值
* `version` 不得为负数
* 创建和更新时间符合当前时间字段约定

## 12.1 位置唯一性

本任务不强制为 `position` 建立立即生效的唯一约束，除非 `design.md` 证明现有 D1 更新策略可以安全处理批量交换。

原因：

* 拖拽重排会批量调整多个位置
* SQLite 立即唯一约束可能使交换操作复杂化
* 后续服务层会通过原子批量操作维护顺序

即使数据库不使用唯一约束，后续服务层仍必须防止重复或缺失位置。

## 12.2 排序模式约束

优先在数据库层使用 `CHECK` 或当前项目一致的约束方式限制非法 `sort_mode`。

共享 Zod Contract 也必须进行相同限制。

# 13. `board_groups` 表

## 13.1 表职责

`board_groups` 表示板块与群组之间的多对多关系。

它支持：

* 一个板块包含多个群组
* 一个群组加入多个板块
* 同一群组在同一板块内只能出现一次
* 每个板块拥有独立的成员人工顺序

## 13.2 逻辑字段

至少包含：

```text
board_id
group_id
position
created_at
```

## 13.3 字段含义

### `board_id`

关联 `boards.id`。

### `group_id`

关联现有群组表主键。

### `position`

群组在该板块中的标准人工位置。

无论板块公开排序模式是：

* 正序
* 倒序
* 每小时随机

数据库中的 `position` 始终代表管理员维护的标准顺序。

### `created_at`

群组加入该板块的时间。

该字段不等同于群组创建时间或发布时间。

# 14. `board_groups` 约束

## 14.1 复合主键

必须建立：

```text
PRIMARY KEY (board_id, group_id)
```

保证同一群组不能重复加入同一个板块。

## 14.2 外键

应建立：

* `board_id` → `boards.id`
* `group_id` → 群组表主键

外键行为必须与当前 D1 和项目 migration 规范兼容。

## 14.3 删除板块

删除板块时，其板块成员关联应一并删除。

优先使用：

```text
ON DELETE CASCADE
```

或当前项目已有等效机制。

删除板块不得删除群组本身。

## 14.4 删除群组

群组永久删除后，不得留下孤立的板块关联。

可以使用外键级联作为最后一道数据完整性保护，但不得仅依赖级联绕过现有永久删除状态机。

后续子任务 05 仍需将板块关联纳入业务流程和测试。

## 14.5 群组下架

群组变为已下架时：

* 不删除 `board_groups`
* 不改变成员 `position`
* 公开查询时由后续任务过滤

本任务不得将下架状态转换与关联删除绑定。

## 14.6 群组进入回收站

产品规则要求进入回收站时删除全部板块关联。

本任务只建立支持该行为的表结构和索引。

实际将回收站状态变化与关联删除原子接入现有状态机，由子任务 05 完成。

## 14.7 位置约束

`position` 必须为非负整数。

本任务不强制位置唯一，后续由服务层原子维护。

# 15. 数据库索引

## 15.1 `last_published_at` 查询索引

需要建立适合以下查询模式的索引：

```text
status = 已发布
ORDER BY last_published_at DESC, id DESC
```

具体索引可以是：

* 复合索引
* 部分索引
* 与当前 SQLite/D1 最佳实践兼容的其他索引

最终方案由 `design.md` 基于真实表结构决定。

## 15.2 板块排序索引

至少支持：

```text
boards ORDER BY position
```

建议索引：

```text
boards(position, id)
```

实际字段顺序根据查询计划确定。

## 15.3 板块成员索引

至少支持：

```text
WHERE board_id = ?
ORDER BY position, group_id
```

建议索引：

```text
board_groups(board_id, position, group_id)
```

## 15.4 按群组清理关联

为支持群组进入回收站或永久删除时快速查找全部关联，应支持：

```text
WHERE group_id = ?
```

复合主键以 `board_id` 开头，通常不能完全代替单独的 `group_id` 索引。

需要根据 SQLite 查询计划决定是否新增：

```text
board_groups(group_id)
```

## 15.5 索引命名

索引名称必须遵循项目当前 migration 命名规范。

不得建立重复或无法被实际查询使用的索引。

# 16. 默认“自定板块”

## 16.1 初始化规则

新 migration 应在板块表创建完成后，自动创建一个空板块：

```text
title = 自定板块
```

默认建议：

```text
is_enabled = true
sort_mode = manual_asc
position = 0
version = 初始版本
```

时间字段使用 migration 或数据库约定的合法初始化时间。

## 16.2 普通数据身份

默认“自定板块”只是初始化数据，不是系统保留对象。

它可以：

* 重命名
* 关闭
* 编辑
* 添加成员
* 删除

删除后允许板块数量为 0。

## 16.3 不得自动重建

默认板块只能在首次数据库迁移或初始化时创建。

管理员删除后：

* 应用启动不得重新创建
* 页面加载不得重新创建
* 后续普通 API 调用不得重新创建
* 后续无关 migration 不得重新创建

## 16.4 幂等语义

“幂等”不等于每次运行应用都检查并补回默认板块。

本任务中的幂等要求是：

* 同一数据库初始化流程不会插入重复默认板块
* migration runner 不会因重复执行流程产生多个默认板块
* 测试数据库重复初始化过程结果稳定
* 迁移记录能够防止同一 migration 重复应用

不得为了通过幂等测试，在运行时持续执行：

```text
如果板块为 0，则创建默认板块
```

这会违反允许零板块的产品规则。

# 19. 显示宽度算法

## 19.1 目标

建立一个确定、可测试、跨运行时一致的纯函数，例如：

```ts
measureDisplayWidth(value: string): number
```

最终名称遵守共享工具命名规范。

## 19.2 字素簇

算法应优先按用户可见字素簇处理，而不是按：

* UTF-16 code unit
* JavaScript `string.length`
* 单个 Unicode code point

以下内容应视为一个可见单元：

* 带组合音标的拉丁字母
* 带肤色修饰符的 Emoji
* 由 ZWJ 连接的家庭 Emoji
* 国旗 Emoji
* 其他合法组合字素

## 19.3 宽度规则

每个可见字素簇按照以下规则计算。

### 宽度 2

* 中文汉字
* 日文宽字符
* 韩文宽字符
* East Asian Width 为 Wide 的字符
* East Asian Width 为 Fullwidth 的字符
* Emoji 字素簇

### 宽度 1

* ASCII
* 普通半角拉丁字符
* 数字
* 半角标点
* 带组合音标的普通拉丁字母字素
* East Asian Width 为 Narrow、Halfwidth、Neutral 或 Ambiguous 且不属于 Emoji 的字符

对 Ambiguous 字符默认按 1 计算，避免在不同系统字体下产生前后端差异。

## 19.4 空白字符

建议规则：

* 普通空格：1
* 全角空格：2
* Tab：按 4 个宽度单位计算
* `\r\n` 先规范化为单个换行
* 每个换行按 1 个宽度单位计算

换行不能完全按 0 处理，否则可通过大量空行绕过简介限制。

## 19.5 控制字符

除允许的换行和 Tab 外，不可见控制字符应：

* 被现有清洗逻辑拒绝
* 或按共享 Schema 规则处理

不得允许大量零宽控制字符绕过长度限制。

Emoji 内合法的：

* ZWJ
* 变体选择符
* 组合修饰符

不应单独增加额外宽度。

## 19.6 运行时一致性

实现必须在以下环境结果一致：

* 现代浏览器
* Node/Vitest
* Cloudflare Workers
* Workers Vitest

如使用 `Intl.Segmenter`：

* 必须确认目标运行时支持
* 测试环境需要一致
* 如存在不一致，应提供确定性 fallback

如引入 Unicode 处理依赖：

* 必须说明必要性
* 评估包体积
* 不得引入大型无关依赖
* 前后端必须使用同一版本和同一实现

# 38. 性能要求

## 38.1 字符宽度

显示宽度函数会在用户输入时频繁执行，必须避免明显卡顿。

对最多 1000 宽度单位的简介，单次计算应足够轻量。

不得每次输入都：

* 动态加载大型 Unicode 数据
* 创建不必要的大量对象
* 执行网络请求
* 触发昂贵 DOM 测量

该函数应是纯文本计算，不依赖 Canvas 或实际浏览器字体渲染。

## 38.2 数据库

新增索引应服务真实查询。

不得为尚未存在的查询建立大量冗余索引，增加写入成本。

## 38.3 Migration

回填应适合当前数据规模，避免逐行从应用层发起大量数据库请求。

优先使用 SQL 集合更新或安全的批处理方式。
