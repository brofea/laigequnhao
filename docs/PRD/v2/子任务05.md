# 1. 背景

子任务 04 已建立本次 V2 升级所需的数据基础，包括：

* 群组字段 `last_published_at`
* `boards` 表
* `board_groups` 表
* 板块和成员排序位置
* 板块排序模式
* 外键、索引和约束
* 默认“自定板块”
* 板块基础共享类型
* 群组状态转换基础
* 标题和简介显示宽度规则

本任务负责在这些基础上实现完整的板块后端领域能力。

板块不是单纯的两张表和若干 CRUD route。它同时涉及：

* 管理员认证
* CSRF
* 版本冲突
* 板块和成员排序
* 多行原子更新
* 一次性突变令牌
* 群组状态过滤
* 回收站状态机
* 公开数据脱敏
* 每小时稳定随机
* 并发管理员修改
* 零板块和空板块状态

因此，本任务必须以正式领域模型完成 repository、service 和 route 分层，不能把排序、状态过滤和并发控制分散在前端或 route 中。

# 2. 任务目标

## 2.1 完成板块管理后端

管理员能够通过受保护的 API：

* 获取全部板块
* 创建板块
* 编辑板块
* 启用板块
* 关闭板块
* 删除板块
* 调整板块顺序
* 获取板块成员
* 搜索可添加群组
* 添加已发布群组
* 添加已下架群组
* 移除成员
* 上移成员
* 下移成员
* 修改板块内部排序模式

## 2.2 完成公开板块查询

公开端能够获取：

* 所有已启用板块
* 按板块位置排序
* 每个板块中当前已发布的群组
* 按板块排序模式组织后的群组顺序
* 启用但无公开成员的空板块

公开接口不得泄露：

* 已下架群组
* 回收站群组
* 已删除群组
* 板块版本号
* 管理内部字段
* 已下架群组数量或身份
* 管理员专用状态信息

## 2.3 完成数据一致性规则

所有板块排序和成员顺序修改必须：

* 原子完成
* 保持位置连续或满足项目确定的位置规范
* 防止重复成员
* 防止并发覆盖
* 防止部分更新
* 在失败时完整回滚

## 2.4 接入群组状态机

群组状态变化时：

* 已发布变为已下架：保留板块关联
* 已下架重新发布：恢复公开显示，无需重新添加
* 群组进入回收站：原子删除全部板块关联
* 从回收站恢复：不自动恢复原板块关联
* 永久删除：不得留下孤立关联

## 2.5 完成安全控制

所有管理端写接口必须继续使用：

* 管理员身份验证
* CSRF 双提交保护
* Zod 校验
* 版本冲突保护
* 一次性突变令牌或现有原子批量模式
* 统一错误响应

# 6. 领域模型

## 6.1 板块

板块至少具有以下领域属性：

```text
id
title
isEnabled
position
sortMode
version
createdAt
updatedAt
```

实际命名遵循当前数据库 snake_case 与领域对象 camelCase 的映射规范。

## 6.2 板块成员

板块成员关系至少具有：

```text
boardId
groupId
position
createdAt
```

管理端成员 DTO 还需要组合必要的群组摘要，例如：

* 群组标题
* 群组状态
* 可能需要的版本或编辑标识

不得将完整群组敏感数据复制进 `board_groups` 表。

## 6.3 排序模式

共享排序模式固定为：

```ts
type BoardSortMode =
  | 'manual_asc'
  | 'manual_desc'
  | 'hourly_random'
```

不得增加：

* 按点赞排序
* 按发布时间排序
* 每次请求随机
* 每日随机
* 前端自由字段排序

除非后续总 PRD 另行修改。

# 7. 分层职责

## 7.1 Route 层

Route 只负责：

* 读取请求
* 执行管理员认证
* 执行 CSRF 校验
* 使用共享 Zod Schema 解析输入
* 调用 service
* 将领域错误映射为统一 HTTP 响应
* 返回共享 Contract 规定的数据

Route 不负责：

* 直接执行 SQL
* 计算成员位置
* 实现每小时随机
* 判断群组状态能否添加
* 判断版本冲突
* 执行多行排序更新
* 拼接敏感公开过滤条件

## 7.2 Service 层

Service 负责：

* 领域规则
* 状态校验
* 版本校验
* 板块排序规则
* 成员添加和移动规则
* 并发控制
* 原子批量操作协调
* 公开数据过滤
* 每小时稳定随机
* 回收站关联清理
* repository 调用顺序
* 领域错误定义

## 7.3 Repository 层

Repository 负责：

* D1 查询
* D1 写入
* 按事务或 batch 执行原子操作
* 数据库记录与领域类型映射
* 约束冲突识别
* 查询稳定排序
* 批量位置更新
* 按群组删除全部关联

Repository 不负责：

* HTTP 状态码
* CSRF
* 用户可见错误文案
* 产品层状态选择
* 页面显示逻辑

## 7.4 Adapter 和共享层

如项目使用独立时区、时钟、UUID 或哈希 Adapter，应复用现有能力。

不得在板块 service 中直接依赖不可测试的全局环境。

# 8. 管理端 API 范围

确切路径必须遵循项目现有 API 路由规范，并在本任务 `design.md` 中冻结。

无论最终路径如何，必须提供以下语义能力：

1. 获取板块元数据列表
2. 获取单个板块及成员
3. 创建板块
4. 更新板块
5. 删除板块
6. 批量调整板块顺序
7. 查询可添加群组
8. 添加成员
9. 移除成员
10. 上移成员
11. 下移成员

可采用类似以下路由结构，但不得无视现有项目约定机械照搬：

```text
GET    /api/admin/boards
POST   /api/admin/boards
GET    /api/admin/boards/:boardId
PATCH  /api/admin/boards/:boardId
DELETE /api/admin/boards/:boardId

POST   /api/admin/boards/reorder

GET    /api/admin/boards/:boardId/members
GET    /api/admin/boards/:boardId/candidates
POST   /api/admin/boards/:boardId/members
DELETE /api/admin/boards/:boardId/members/:groupId
POST   /api/admin/boards/:boardId/members/:groupId/move
```

是否合并读取接口由 `design.md` 决定，但不得让管理端为了展示一个页面产生明显 N+1 请求。

# 9. 公开 API 范围

至少提供一个公开读取能力，返回：

* 已启用板块
* 按板块位置排序
* 每个板块当前已发布成员
* 成员按照对应 `sortMode` 排序
* 空板块

示意路由：

```text
GET /api/boards
```

实际路径遵循当前公开 API 规范。

公开接口：

* 不需要管理员认证
* 不需要 CSRF
* 只允许 GET 或项目认可的只读方法
* 必须执行严格公开数据投影
* 不得复用管理端 DTO 直接返回

# 10. 板块管理列表

## 10.1 管理端板块排序

管理端板块列表按：

```text
position ASC
id ASC
```

返回。

`id` 作为稳定次排序字段。

## 10.2 返回内容

管理端板块元数据至少包括：

* ID
* 标题
* 启用状态
* 位置
* 排序模式
* 版本
* 成员总数
* 已发布成员数量
* 已下架成员数量
* 创建时间
* 更新时间

是否在列表中直接返回全部成员，由 `design.md` 根据现有架构和性能决定。

推荐方式：

* 板块列表返回元数据和成员数量
* 单个板块成员按需加载
* 后端支持批量读取，避免管理端展开多个板块时产生无控制的请求风暴

## 10.3 零板块

当管理员删除全部板块后，列表返回：

```json
[]
```

不得：

* 自动创建默认板块
* 返回虚拟板块
* 将零板块视为错误
* 在 route 初始化时补建“自定板块”

# 11. 创建板块

## 11.1 输入

至少包括：

* `title`
* `isEnabled`
* `sortMode`

位置由服务端确定。

客户端不得直接通过创建接口指定任意 `position`，除非 `design.md` 证明现有架构需要且有完整校验。

## 11.2 初始位置

新板块默认追加到所有板块末尾：

```text
position = 当前最大 position + 1
```

无板块时：

```text
position = 0
```

## 11.3 初始版本

版本号遵循当前项目版本冲突规范。

不得单独为板块建立与群组完全不同的版本语义。

## 11.4 标题

标题必须：

* trim
* 非空
* 满足共享 Schema
* 不接受仅空白字符
* 不允许不可见控制字符绕过

如子任务 04 尚未冻结板块标题最大长度，本任务必须在 `design.md` 中依据现有产品和安全规范明确一个合理上限，并同步总任务文档。

不得仅依赖数据库 TEXT 无上限存储。

## 11.5 同名板块

产品目前未规定标题唯一。

因此默认允许多个板块使用相同标题。

不得擅自增加全局唯一约束。

# 12. 更新板块

## 12.1 可修改字段

至少允许：

* 标题
* 启用状态
* 排序模式

板块位置不通过普通更新接口修改，而通过专门的批量排序操作修改。

## 12.2 版本要求

客户端必须提交预期版本。

服务端更新条件必须包含：

```text
id = boardId
version = expectedVersion
```

成功更新后：

* 版本递增
* `updated_at` 更新
* 未修改字段保持不变

## 12.3 并发冲突

预期版本与数据库不一致时：

* 不更新任何字段
* 返回统一版本冲突错误
* 返回当前最新板块快照或项目现有冲突结构
* 不静默覆盖其他管理员修改

## 12.4 启用和关闭

启用或关闭属于普通板块更新。

关闭板块后：

* 公开接口不返回该板块
* 成员关联保留
* 成员位置保留
* 管理端仍可读取和修改
* 不影响群组本身状态

重新启用后：

* 已发布成员重新出现在公开端
* 已下架成员继续隐藏
* 原人工顺序保留

## 12.5 排序模式修改

修改 `sortMode` 后：

* 不改写 `board_groups.position`
* 不批量重新排列数据库成员
* 只改变公开展示时的读取顺序
* 版本递增

从 `hourly_random` 切回手动模式时，应恢复使用原人工位置。

# 13. 删除板块

## 13.1 输入

删除操作必须携带：

* 板块 ID
* 预期版本
* 必要的一次性突变令牌，如当前项目安全模式要求

## 13.2 删除行为

成功删除板块后：

* 删除板块记录
* 删除该板块全部 `board_groups`
* 不删除任何群组
* 不修改群组状态
* 不删除 R2 资源
* 其余板块位置应按确定规则重新整理

## 13.3 位置整理

删除板块后应将后续板块位置压缩，避免长期出现无控制的巨大空洞。

例如删除位置 2：

```text
0, 1, 2, 3, 4
```

应调整为：

```text
0, 1, 2, 3
```

板块删除与位置整理必须原子完成。

## 13.4 删除最后一个板块

允许删除最后一个板块。

结果为零板块，不自动重建默认板块。

## 13.5 版本冲突

如果删除时版本不一致：

* 不删除板块
* 不删除成员
* 不调整其他板块位置
* 返回版本冲突

# 14. 板块顺序调整

## 14.1 产品行为

管理端允许通过拖拽调整板块之间的顺序。

前端拖拽属于子任务 08，本任务只负责接受和验证新的完整顺序。

## 14.2 推荐输入

排序接口推荐接收完整板块顺序：

```ts
{
  boardIds: string[]
  expectedVersions: Record<string, number>
  mutationToken: string
}
```

实际类型依据项目 ID 和突变令牌规范确定。

## 14.3 完整集合校验

服务端必须验证：

* 请求中的 ID 不重复
* 所有 ID 均存在
* 请求没有遗漏当前板块
* 请求没有包含额外未知板块
* 版本信息完整
* 所有预期版本匹配

不得允许客户端只提交局部位置后让服务端猜测整体顺序，除非 `design.md` 证明局部移动更符合现有模式且同样具备原子一致性。

## 14.4 原子更新

全部板块位置必须在一个原子操作中更新。

不得出现：

* 一半位置已更新
* 一半位置未更新
* 多个板块得到同一最终位置
* 请求失败但部分版本已增加

## 14.5 版本更新

参与排序的板块应按照设计好的统一规则更新版本。

推荐：

* 所有位置发生变化的板块版本递增
* 未变化板块版本不递增

若为降低复杂度而统一递增全部板块版本，必须在 `design.md` 中说明，并保证前端冲突处理可理解。

## 14.6 并发冲突

任意一个板块版本不匹配时：

* 整个排序失败
* 不修改任何位置
* 返回最新板块顺序
* 前端后续可以回滚乐观排序

# 15. 一次性突变令牌

## 15.1 使用范围

以下多行操作必须复用现有突变令牌模式：

* 板块批量重排
* 删除板块并压缩位置
* 成员上移
* 成员下移
* 移除成员并压缩位置
* 群组进入回收站并删除全部板块关联
* 其他会更新多条记录的操作

## 15.2 令牌语义

令牌必须：

* 由可信客户端流程生成
* 一次性使用
* 重复提交不能重复执行变更
* 与现有 D1 批量操作模式一致
* 在操作成功后标记完成
* 在失败时按现有模式允许安全重试或明确拒绝

不得另建第二套不兼容的幂等令牌系统。

## 15.3 重放请求

相同突变令牌重复提交时，应遵循现有项目规则：

* 返回原结果
* 或明确返回已使用冲突

不得重复移动、重复删除或再次递增版本。

# 16. 板块成员列表

## 16.1 管理端成员排序

管理端始终按标准人工位置显示：

```text
position ASC
groupId ASC
```

即使板块公开排序模式是：

* `manual_desc`
* `hourly_random`

管理端成员编辑顺序仍使用标准人工位置。

这样可以保证管理员上移、下移行为可预测。

## 16.2 返回字段

管理端成员 DTO 至少包括：

* `boardId`
* `groupId`
* 成员位置
* 加入板块时间
* 群组标题
* 群组状态
* 群组当前版本或编辑所需标识
* 是否允许上移
* 是否允许下移

`canMoveUp` 和 `canMoveDown` 可以由前端根据索引计算，也可以由后端返回。具体由 `design.md` 决定。

## 16.3 状态范围

正常成员列表允许出现：

* 已发布群组
* 已下架群组

不得正常出现：

* 回收站群组
* 永久删除群组
* 不存在的孤立记录

如发现异常关联，不能直接在公开接口泄露，应记录服务端错误或进行安全过滤。

## 16.4 不分页

产品规定板块成员表固定高度并内部滚动，不使用页码分页。

因此成员接口应支持返回该板块全部成员。

实现仍需：

* 使用高效单次查询
* 避免逐成员 N+1
* 使用稳定排序
* 记录极端成员数量的性能风险

不得擅自增加硬性成员数量上限。

# 17. 可添加群组查询

## 17.1 目的

管理端添加成员选择器需要搜索可加入当前板块的群组。

后端必须提供足够能力支持：

* 按标题等现有管理搜索能力查询
* 区分已发布和已下架
* 排除回收站
* 防止重复添加

## 17.2 可选状态

允许候选群组：

* 已发布
* 已下架

不允许候选群组：

* 回收站
* 永久删除
* 不存在记录

其他状态如草稿、待审核是否可加入，应以当前真实状态机和修订后的总 PRD 为准。

用户已经明确允许已下架成员，但尚未明确允许草稿或待审核群组。

默认实现不得擅自扩大为所有非回收站状态。

若真实状态机存在更多状态，必须在 `design.md` 中明确候选状态集合。

## 17.3 已加入群组

已经加入当前板块的群组可以：

* 从结果中排除
* 或返回 `alreadyMember: true`

具体方式由管理端 API 设计决定。

无论采用哪种方式，添加接口本身仍必须防止重复关联。

## 17.4 查询分页

候选群组可能较多。

可复用现有管理端群组搜索或建立轻量候选接口。

具体分页方式可采用：

* 页码分页
* cursor pagination
* 限制结果的搜索建议

不得一次返回数据库中的全部群组作为选择器候选。

该查询分页不等于板块成员表分页。

# 18. 添加成员

## 18.1 输入

至少包括：

* 板块 ID
* 群组 ID
* 板块预期版本
* 必要的突变令牌

## 18.2 板块状态

允许向以下板块添加成员：

* 已启用板块
* 未启用板块

板块是否公开不影响管理编辑能力。

## 18.3 群组状态

允许添加：

* 已发布群组
* 已下架群组

不得添加：

* 回收站群组
* 永久删除群组
* 不存在群组
* 产品未允许的其他状态

## 18.4 新成员位置

新成员默认追加到标准人工顺序末尾：

```text
position = 当前最大 position + 1
```

无成员时：

```text
position = 0
```

这一规则与当前 `sortMode` 无关。

例如板块当前为 `manual_desc`，新成员仍追加到标准位置末尾，公开端倒序后可能显示在前部。这是排序模式的预期结果。

## 18.5 重复成员

同一群组已在当前板块中时：

* 不新增第二条记录
* 不修改原位置
* 不递增无关版本
* 返回明确领域冲突

不得把数据库唯一约束异常直接作为不透明 500 返回。

## 18.6 成功后版本

成功添加成员后：

* 板块版本递增
* 板块 `updated_at` 更新
* 新成员位置确定
* 返回更新后的板块版本和成员数据

成员变化属于板块配置变化，必须参与版本冲突保护。

# 19. 移除成员

## 19.1 语义

移除成员只删除：

```text
board_groups(boardId, groupId)
```

不得：

* 删除群组
* 下架群组
* 将群组移入回收站
* 删除图片
* 删除加群方式
* 修改群组版本

## 19.2 位置压缩

移除成员后，后续成员位置应压缩。

例如：

```text
0, 1, 2, 3
```

移除位置 1 后变为：

```text
0, 1, 2
```

删除关联和位置压缩必须原子完成。

## 19.3 不存在成员

请求移除不存在的成员时，应遵循项目统一语义：

* 返回 404
* 或幂等成功

最终规则必须在 `design.md` 中冻结，并与现有删除接口保持一致。

不得因找不到关联而误删群组。

## 19.4 版本

成功移除后：

* 板块版本递增
* `updated_at` 更新

版本冲突时不执行任何删除或位置调整。

---

# 20. 成员上移和下移

## 20.1 管理语义

上移和下移始终基于标准人工位置。

与公开排序模式无关。

例如：

* `manual_desc` 只影响公开展示
* 管理端点击“上移”仍使成员的标准 `position` 减少
* `hourly_random` 下仍允许调整人工位置，以便未来切回手动模式

## 20.2 上移

目标成员与前一个成员交换位置。

第一项：

* 不允许继续上移
* 返回明确边界错误或幂等不变结果
* 不应导致版本无意义递增

## 20.3 下移

目标成员与后一个成员交换位置。

最后一项：

* 不允许继续下移
* 返回明确边界错误或幂等不变结果
* 不应导致版本无意义递增

## 20.4 输入形式

推荐使用：

```ts
{
  direction: 'up' | 'down'
  expectedVersion: number
  mutationToken: string
}
```

客户端不应直接提交两个任意位置值，让服务端无条件交换。

## 20.5 原子性

交换两条成员位置和递增板块版本必须原子完成。

失败时：

* 两条成员位置均保持原值
* 板块版本不变
* 不产生重复位置

## 20.6 并发

移动前必须基于数据库当前标准顺序重新读取相邻成员。

不得仅信任客户端提供的旧邻居 ID。

# 21. 板块公开排序

## 21.1 手动正序

`manual_asc`：

```text
position ASC
groupId ASC
```

## 21.2 手动倒序

`manual_desc`：

```text
position DESC
groupId DESC 或确定的稳定次排序
```

次排序必须稳定。

手动倒序不得修改数据库位置。

## 21.3 每小时随机

`hourly_random`：

* 同一个站点自然小时内顺序固定
* 到下一个站点自然小时后形成新顺序
* 刷新页面不会在同一小时改变顺序
* 不使用数据库随机排序
* 不写回 `position`
* 不运行定时任务
* 不依赖单个 Worker 实例内存状态
* 多个 Cloudflare Worker 实例结果一致

# 22. 每小时稳定随机算法

## 22.1 输入

排序结果至少由以下输入决定：

```text
boardId
站点小时槽位
groupId
```

可以附加固定算法版本或站点种子，但不得依赖请求时间中的分钟、秒或随机数。

## 22.2 小时槽位

小时槽位必须使用站点配置时区。

不得使用：

* Worker 服务器本地时区
* 用户浏览器时区
* 请求 IP 推断时区
* UTC 小时直接代替站点小时，除非站点配置明确为 UTC

小时槽位应表示站点时区中的确定自然小时，例如：

```text
2026-07-31T11
```

实际序列化格式由技术设计确定。

## 22.3 确定性

同样的：

* 板块 ID
* 小时槽位
* 群组 ID 集合

在以下环境必须产生相同顺序：

* 不同 Worker 实例
* Workers Vitest
* 重复请求
* 同一小时内的刷新

## 22.4 排序键

每个群组生成稳定排序键，例如：

```text
hash(boardId + hourSlot + groupId)
```

然后按照：

```text
hash ASC
groupId ASC
```

排序。

哈希碰撞时必须使用群组主键作为稳定次排序。

## 22.5 哈希选择

哈希算法必须：

* 确定
* 跨运行时一致
* 计算成本合理
* 不依赖秘密
* 不用于安全认证

可以复用项目已有确定性哈希工具。

不得使用 JavaScript `Math.random()`。

## 22.6 成员变化

每小时固定的是排序规则，不是数据快照。

同一小时内发生以下变化时：

* 新成员加入板块
* 成员移除
* 已下架成员重新发布
* 已发布成员下架

下一次请求应反映最新成员集合，并使用当前小时槽位对新集合进行确定排序。

不得为了保持旧序列而隐藏刚发布成员到下一个小时。

## 22.7 缓存

如公开接口使用缓存：

* 不得让禁用板块长期继续公开
* 不得让已下架群组长期继续公开
* 不得超过下一个小时仍返回旧随机顺序
* 应考虑管理修改后的缓存失效

本任务不强制必须缓存。

如果不实现缓存，应在 `design.md` 中说明查询性能足够。

# 23. 公开板块查询规则

## 23.1 板块过滤

只返回：

```text
is_enabled = true
```

未启用板块完全不出现在公开结果中。

## 23.2 板块顺序

公开板块按：

```text
position ASC
id ASC
```

返回。

## 23.3 成员过滤

每个板块只返回当前状态为已发布的群组。

已下架成员：

* 保留数据库关联
* 不出现在公开 DTO
* 不计入公开成员列表
* 不泄露标题、头像、平台或其他信息

回收站和已删除群组同样不得返回。

## 23.4 空板块

启用板块即使：

* 从未添加成员
* 只包含已下架成员
* 成员已全部进入回收站

也应在公开接口中返回，成员列表为空。

这样公开端可以按照产品规则展示板块空状态。

## 23.5 零板块

没有已启用板块时返回空数组。

不视为错误。

## 23.6 公开群组 DTO

公开板块成员应使用公开群组卡片所需 DTO，至少包含后续卡片需要的数据：

* 群组 ID
* 头像
* 标题
* 平台
* 简介
* 点赞数
* 当前设备点赞状态所需信息，如现有公开 DTO 支持

具体点赞状态可能依赖请求设备标识，不得因复用板块接口破坏现有匿名点赞隐私模型。

不得直接返回管理端完整 Group DTO。

## 23.7 加群方式

公开板块列表用于卡片展示，卡片不直接显示加群方式。

因此板块列表接口原则上不需要返回完整二维码、群号或加群链接。

群组详情由专门的公开详情能力提供。

这可以降低响应体积和敏感数据暴露面。

# 24. 公开查询性能

## 24.1 禁止 N+1

不得：

1. 先查询板块
2. 再为每个板块逐个查询成员
3. 再为每个成员逐个查询群组

推荐使用：

* 一次板块查询
* 一次批量成员与群组查询
* 服务层按 `boardId` 分组

或其他能够控制查询次数的方案。

## 24.2 数据量

板块成员数量没有产品硬上限。

因此实现需要：

* 使用索引
* 只选择公开卡片必要字段
* 不返回管理字段
* 不返回完整加群方式
* 避免重复序列化同一群组的不必要大对象

一个群组出现在多个板块时，公开响应中允许在对应板块重复出现。

## 24.3 查询计划

`design.md` 应记录关键查询及其索引匹配。

如测试基础允许，应检查 SQLite 查询计划或至少验证索引存在并符合查询条件。

# 25. 公开数据安全

## 25.1 状态过滤位置

公开状态过滤必须在后端查询或 service 投影中完成。

不得依赖前端收到已下架成员后自行隐藏。

## 25.2 竞态

公开查询期间群组被下架时，下一次完整请求必须不再返回该群组。

无需建立跨请求强一致快照，但单次响应不得混合明显不合法状态。

## 25.3 错误信息

公开接口不得返回：

* “某板块有 3 个下架成员”
* 下架群组 ID
* 回收站关联详情
* 管理员版本冲突
* 内部 mutation token
* SQL 错误
* 内部表名

## 25.4 缓存头

如使用 CDN 或浏览器缓存，必须确保公开状态变化不会因过长缓存造成敏感数据继续可见。

安全优先于缓存命中率。

# 26. 回收站关联清理

## 26.1 产品规则

群组进入回收站时：

* 删除该群组在所有板块中的关联
* 群组状态变化与关联删除必须原子完成
* 恢复后不自动恢复关联

## 26.2 接入现有状态机

Agent 必须根据子任务 01 和 04 的审计结果，定位真实的：

* 移入回收站 route
* service
* repository
* D1 batch
* 突变令牌
* 版本检查

板块清理必须接入现有正式调用链。

不得：

* 在 route 成功后再额外发第二次删除请求
* 由管理端前端逐板块删除
* 使用异步后台补偿作为正常流程
* 先返回成功再尝试清理关联

## 26.3 原子操作

一次移入回收站操作至少包括：

1. 验证群组当前状态和版本
2. 更新群组为回收站状态
3. 删除所有 `board_groups WHERE group_id = ?`
4. 完成现有状态机要求的其他 D1 变更
5. 提交批量操作

任一步失败：

* 群组状态不变化
* 板块关联不变化
* 不返回成功

## 26.4 对板块位置的处理

同一个群组可能属于多个板块。

删除关联后，应为每个受影响板块整理成员位置。

不得留下无控制的位置空洞。

所有受影响板块的位置整理和版本变化规则必须在 `design.md` 中冻结。

推荐：

* 每个受影响板块成员位置压缩
* 每个受影响板块版本递增
* `updated_at` 更新

## 26.5 并发

如果另一个管理员同时编辑受影响板块，回收站操作必须使用现有事务和版本策略避免产生部分结果。

群组进入回收站属于更高优先级的状态安全操作。

即使某个板块客户端持有旧版本，回收站清理也不能因为 UI 未同步而保留非法关联。

建议：

* 回收站状态操作在数据库中强制清理关联
* 受影响板块版本递增
* 后续板块编辑请求通过版本冲突刷新

## 26.6 恢复

群组从回收站恢复后：

* 不重新插入任何 `board_groups`
* 不尝试从日志猜测旧板块
* 不保留隐藏的恢复映射
* 管理员需要手动重新添加

管理端提示属于子任务 08。

# 27. 永久删除兼容

## 27.1 正常路径

正常情况下，群组进入回收站时已经删除全部板块关联。

永久删除时不应再存在关联。

## 27.2 防御性处理

永久删除流程仍应：

* 确认外键不会阻止删除
* 允许级联作为数据完整性后盾
* 在异常旧数据存在关联时安全清理或失败
* 不影响资源收集和 R2 清理顺序

## 27.3 不得破坏四阶段状态机

板块关联处理不得改变：

1. 验证软删除
2. 收集独占资源
3. R2 清理
4. D1 批量删除

不得因为外键级联而在资源收集前提前删除群组记录。

# 28. 板块版本模型

## 28.1 版本涵盖范围

板块版本表示板块配置的完整版本。

以下成功操作应使板块版本递增：

* 修改标题
* 启用
* 关闭
* 修改排序模式
* 添加成员
* 移除成员
* 上移成员
* 下移成员
* 因回收站清理删除成员
* 板块位置变化

## 28.2 不递增场景

以下情况不应递增版本：

* 只读查询
* 重复但未生效的边界移动
* 版本冲突
* 校验失败
* 重复成员添加失败
* 不存在成员移除失败
* 已使用突变令牌的重放请求，除非现有幂等机制返回原结果

## 28.3 响应

成功写操作应返回：

* 新版本
* 更新后的核心对象
* 必要的最新顺序

前端不应通过猜测 `version + 1` 维护状态。

# 29. 并发场景

必须明确处理以下并发。

## 29.1 两个管理员同时编辑同一板块标题

一个成功，一个收到版本冲突。

## 29.2 一个管理员关闭板块，另一个添加成员

两个操作不能静默覆盖。

由于未启用板块仍允许编辑，冲突解决后添加操作仍可重新提交。

## 29.3 两个管理员同时移动同一成员

只能有一个基于当前版本成功。

## 29.4 一个管理员删除板块，另一个编辑板块

删除或编辑之一成功，另一个返回不存在或版本冲突。

不得重新创建已删除板块。

## 29.5 群组进入回收站，同时管理员向板块添加该群组

最终不得留下回收站群组关联。

添加 service 必须在写入时验证群组当前状态。

不能只依赖候选列表几秒前的状态。

## 29.6 群组下架，同时公开查询

下架完成后的后续公开查询不返回该群组。

关联保持。

# 38. 缓存策略

## 38.2 公开接口

* 不缓存
* 使用短期缓存
* 使用不超过小时边界的缓存

具体由 `design.md` 决定。

任何缓存方案都不得使已下架群组在明显过长时间内继续公开。

若当前时间距下一小时仅 3 分钟，缓存不能固定为 60 分钟。

* 每个受影响板块版本正确

关联同样删除。

## 51.6 恢复
