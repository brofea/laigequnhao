# 1. 背景

当前项目的公开端、管理端、后端 API、数据库、对象存储、安全机制及自动化测试均已成型。

本次 V2 升级将涉及：

* 公开首页信息架构重构
* 群组卡片和详情弹窗重构
* 自定义板块及板块管理
* 深色模式和统一设计语言
* 管理端页码分页
* 管理端响应式表格
* 数据库字段及表结构扩展
* 全量自动化测试与视觉回归

由于此次升级范围较大，且项目中已经存在大量 Spec、归档任务、领域规则和历史实现，不能直接依据新 PRD 开始编码。

在正式实施前，必须先核对：

1. 当前代码真实实现了什么
2. 当前 Spec 规定了什么
3. 当前实现和 Spec 是否一致
4. V2 总 PRD 是否与现有架构、数据模型或领域规则冲突
5. V2 总 PRD 中是否存在基于错误假设制定的需求
6. 哪些现有能力可以直接复用
7. 哪些需求需要修改 PRD 后再进入设计和实施阶段

本任务负责完成上述事实核验，并据此修订 V2 总 PRD。

# 2. 任务目标

## 2.1 核心目标

在不修改业务代码的前提下，完整理解当前项目的实现、约束、历史决策和测试覆盖情况，并核对它们与 V2 总 PRD 之间的关系。

本任务最终应回答：

* 当前系统的真实行为是什么
* 当前 Spec 与真实代码是否一致
* V2 PRD 中哪些内容可以直接实施
* V2 PRD 中哪些内容需要补充
* V2 PRD 中哪些内容与现有系统冲突
* 哪些冲突可以通过技术方案解决
* 哪些冲突需要产品决策
* 后续每个子任务实际会影响哪些文件和模块

## 2.2 PRD 改进目标

审计结果必须用于改进 V2 总 PRD。

允许根据代码和 Spec 证据：

* 修正错误的现状描述
* 补充遗漏的约束
* 调整不合理的任务边界
* 补充迁移要求
* 补充兼容性要求
* 补充验收条件
* 补充测试要求
* 更正字段名、状态名、路由名和模块名
* 标记仍需用户决策的问题

不得未经用户授权擅自改变已经明确冻结的产品目标。

# 5. 审计方法

## 5.1 代码证据优先

所有关于当前系统行为的结论必须附带证据。

证据至少包括以下一种：

* 文件路径和符号名
* 文件路径和相关行范围
* 测试名称
* migration 名称
* route 路径
* schema 名称
* repository 方法名
* service 方法名

不得只写“当前似乎已经支持”。

## 5.2 Spec、代码和测试三方核对

每个重要领域应分别核对：

| 来源   | 需要回答的问题     |
| ---- | ----------- |
| Spec | 规则应当是什么     |
| 代码   | 实际实现是什么     |
| 测试   | 当前被锁定的行为是什么 |

可能出现以下情况：

* Spec、代码、测试一致
* Spec 和代码一致，但没有测试
* Spec 与代码不一致
* 代码和测试一致，但 Spec 已过时
* 三者互相不一致

每种情况必须单独记录。

## 5.3 不以文件名推断行为

必须阅读调用链，至少追踪至：

```text
前端交互
→ API client
→ route
→ service
→ repository
→ database
```

对于状态修改、回收站和永久删除等高风险逻辑，不得只审查单个文件。

## 5.4 不擅自修复问题

发现 Bug、死代码或设计缺陷时：

* 记录证据
* 记录影响
* 记录建议归属的后续子任务
* 不在本任务中修复

除非问题仅存在于 V2 总 PRD 的文字中，否则不得修改业务实现。

# 6. 冲突分类

所有冲突使用以下等级。

## C0：无冲突

现有实现可直接复用，V2 PRD 不需要调整。

## C1：文档偏差

现有能力与 V2 目标兼容，但 PRD 对字段、文件、状态或术语描述不准确。

处理方式：

* 直接修订 PRD
* 记录修订理由

## C2：可通过技术设计解决

产品目标不需要改变，但现有实现需要扩展或替换。

例如：

* 管理端 keyset 改页码分页
* 新增板块表
* 新增主题初始化脚本

处理方式：

* 补充 PRD 的实现约束和验收条件
* 交由后续 `design.md` 和子任务处理

## C3：跨领域架构冲突

需求会影响多个现有机制，必须调整任务边界或实施顺序。

例如：

* 回收站与板块关联的原子删除
* `last_published_at` 与状态机的集成
* 公开详情接口与现有数据过滤的关系

处理方式：

* 修订总 PRD
* 修订子任务依赖
* 在影响图中标为高风险

## C4：需要产品决策

代码或 Spec 证据表明，现有 PRD 无法唯一确定正确行为，或两个已确认需求无法同时满足。

处理方式：

* 不擅自选择
* 在 `research.md` 中列出选项、影响和推荐
* 在 PRD 中使用明确的待决策标记
* 提交用户确认后再冻结

## C5：阻塞性风险

继续按当前 PRD 实施可能造成：

* 数据损坏
* 下架信息泄露
* 资源生命周期破坏
* 迁移不可逆问题
* 安全机制绕过
* 大量现有测试失效且无替代方案

处理方式：

* 明确标记为阻塞
* 不允许相关后续子任务进入实施
* 必须先完成产品或技术决策

# 9. 交付物三：V2 总 PRD 修改方案

## 9.1 修改方式

本任务允许修改总任务中的 `prd.md`。

修改必须基于：

* Spec 证据
* 代码证据
* 测试证据
* migration 证据

不得仅因个人偏好改变产品规则。

## 9.2 修改分类

每项 PRD 修改必须属于以下一种：

* 事实纠正
* 术语纠正
* 约束补充
* 验收补充
* 测试补充
* 任务边界调整
* 依赖关系调整
* 风险提示
* 待用户决策

## 9.3 已冻结产品决策

除非审计发现 C4 或 C5 冲突，不得擅自改变以下已冻结方向：

* 所有群组和搜索结果使用 Grid
* 发现新群和板块使用 Carousel
* 已下架群组不在公开端显示
* 发现新群按最后一次进入已发布状态的时间排序
* 群组详情使用弹窗
* 详情 URL 使用 `?group=<group_id>`
* 分享按钮复制规范化群组链接
* 卡片简介最多四行
* 板块允许零个
* 默认板块可以删除
* 未启用板块可以编辑
* 管理员可向板块添加已下架群组
* 回收站移除板块关联
* 板块成员表固定高度并内部滚动
* 管理端群组列表每页固定 50 条
* 管理端使用页码分页
* 公开端继续使用 cursor pagination
* 三态主题为自动、浅色、深色
* 手机 Carousel 目标为同时显示至少两张卡片

## 9.4 修改记录

修订后的 PRD 必须增加审计修改记录，包含：

| 修改位置 | 原内容摘要 | 新内容摘要 | 修改原因 | 证据 | 冲突等级 |
| ---- | ----- | ----- | ---- | -- | ---- |

如果存在待用户决策项，不得使用模糊措辞掩盖，必须明确标记。

# 10. 明确禁止事项

本任务不得：

* 修改 Vue 组件
* 修改 TypeScript 业务逻辑
* 修改 Hono route
* 修改 service
* 修改 repository
* 修改 Zod Schema 实现
* 修改数据库表
* 新建正式 migration
* 修改 Tailwind 配置
* 实现主题切换
* 编写板块功能
* 修改分页逻辑
* 修复审计中发现的 Bug
* 删除现有测试
* 更新测试快照
* 安装新依赖
* 执行破坏性数据库命令
* 擅自改变已冻结产品决策
* 为了让 PRD 与现有代码一致而降低明确的 V2 产品目标

允许修改的内容仅限：

* 当前子任务文档
* 总任务 PRD
* 必要的规划索引或任务关系文档

12. 总任务可以依据 `impact-map.md` 安全建立后续子任务
